# 04 接口证据与验证记录

分析日期：2026-10-16。本文件是**证据账本**：记录每个结论来自哪次工具调用、哪个 Evidence ID、哪份本地文件，以及验证到什么程度。
所有结论的强弱以此文件为准；正文（01/02/03）中的"已验证/静态/推断"均指向此处条目。

## 0. 验证载体（先说清楚"谁验证的"）

本文档及 02/03 中所有标为 **真机实测 / 契约验证** 的结论，其验证载体都是**本项目自己的客户端**，不是官方 CMClient：

| 载体 | 位置 | 说明 |
| --- | --- | --- |
| 连接验证原型 | `probe/`（Python 3.12，无第三方依赖） | 2026-10-15 完成首次真实独立登录与自发自收核对（`analysis/connection-probe-result.json`） |
| 桌面客户端预览版 | `coremail_desktop/`（PyInstaller 打包为 `dist/CoremailDesktopPreview/CoremailDesktopPreview.exe`） | 登录、文件夹、列表（每页 50）、阅读、写信、本机草稿（DPAPI 加密）、附件另存、回复/回复全部、已读/星标 |
| 其回归套件 | `tests/`、`docs/releases/` | README 记录最新回归 **197 项（195 通过 / 2 跳过）** |

**为什么必须先讲这一点**：官方 CMClient 只提供"行为日志"这一侧证据（见 §3 各条），
而**请求/响应字段级事实只能由本项目客户端主动发起请求才能得到**。
因此"已验证/契约验证"指的是**本原型与真实服务器交互的结果**，
**不等于**官方客户端的实现细节被完全还原——两者不可互相替代。

**本原型明确未完成的能力**（其 README 自述，与本文档"未验证"清单一致）：
附件上传端到端、移动/删除、服务端搜索、证书加密发送。

（`nf:*` 在所有观测会话中确实一次都没出现）。

**本轮的两项更正**：

1. **"日志里有 IMAP/SMTP 痕迹"是错的**：早先用 `Select-String` 得到的 40/40/91 命中全部是子串假象
   （`News`+`letter` 里的 `ews`、base64 块里的 `imap`/`smtp`）。改为词边界匹配后为 **0**。
   结论应表述为"本账号日志中没有任何标准邮件协议会话"，而不是"见到少量痕迹"。
2. **`supportIMAP: true`** 说明服务端提供 IMAP，但这只证明服务端能力，**不证明客户端可用 IMAP 收发**。
   两者都不能互相替代（见 06 的反向清单）。

**重要纠正（本轮）**：`cim.user:getLunkrMailData` 此前被登记为邮箱服务器接口，实测走的是
**本机代理 `127.0.0.1:9900/adm_api/s/json`**（80 次调用）。02 的端点列已按主机分流，并新增 §1.1「三类主机」。
**自研客户端若照抄该接口，必须路由到本机代理而不是邮箱服务器。**

**协议层内部命名（静态，重要）**：二进制中存在

- `_uploadToFolder->mbox:listMessages`、`_uploadToFolder->mbox:listMessagesV1`（同名 RPC 的 V1/新版两个变体）
- `checkSharedAccount->listSharedAccount`（共享账号检查）
- `mbox:listMessages->HandleResult`（"RPC → 结果处理器"命名约定）

这三条与 §4 的 Ghidra 引用一致，说明协议层按"操作名 + 结果处理器"组织，且部分操作存在版本化变体。

## 5. 验证方法与强度分级

| 级别 | 含义 | 本项目中对应 |
| --- | --- | --- |
| **真机实测** | 对真实服务器执行并核对结果 | 普通密码登录、文件夹 9 个、列表、MIME 下载、自发自收（含唯一标记回查）、回复/回复全部、已读/星标设置→读回→恢复 |
| **契约验证** | 对真实服务器执行单一接口并核对返回结构 | 移动（`attrs.fid`）、服务端搜索（`searchMessages`） |
| **日志统计** | 客户端自身运行日志中的调用与字段 | 31 个接口的调用次数、部分请求体形状、登录响应结构 |
| **静态字面量** | 二进制/网页资源中的字符串、类名、构建路径 | 全部 138 个接口名、18 个端点、54 个错误码、5 套协议适配器 |
| **Ghidra 结构** | 段布局、字符串地址、引用函数、函数体范围 | §4 所列 |

**不得越级**：静态字面量只能证明"该字符串存在于镜像中"，不能证明该接口在当前部署被调用或可用。

## 6. 关键负面结论（同等重要）

1. **运行日志不足以恢复接口契约**：73 个日志文件里，只有少数请求记录了请求体
   （`user:getAttrs{attrIds,optionalAttrIds}`、`user:listDelmsgHistory{limit,loginType,start}`、`mbox:getComposeInfo{id}` 等），
   响应通常只记 `{code}`；完整响应仅 `mbox:getAllFolders` 一类。→ 字段级 schema 必须靠服务端契约验证或反编译。
2. **失败分支不进日志**：54 个 `FA_*` 码在日志中出现 0 次，错误码到处理动作的映射完全没有运行时证据。
3. **网页层不直接发请求**：`ev_dab34191…` 显示安装包内的网页资源没有 HTTP 请求构造，全部经原生桥接。
   → 只分析 `app/` 无法得到接口清单。
4. **无 PDB**：目标引用 `CMClient.pdb` 但本机没有，Ghidra 未恢复原始函数名，全部为 `FUN_*`；
   函数语义只能靠字符串引用与 RTTI 名推断。
5. **日志含第三方数据**：请求行含同域其他同事邮箱（`uid=<name>%40inspur.com`）与会话痕迹。
   所有抽取脚本只保留字段名与类型；**原始日志不得复制进仓库或对外提供**。

### 6.1 线程配对法及其精度上限（本轮新增，重要）

**方法**：响应按"同一线程 id（`T:<tid>`）上最近一次 `func=`"配对，并限制响应与请求的行距 ≤ 4 行。
脚本 `tools/research/extract_contracts_threaded.py`，产物覆盖 `analysis/runtime-interface-contracts.json`。

**结果**：73 个日志文件、31 个接口、**3,430 条成功配对**的响应；副产物是**观测到的 query 参数名**（可靠）：

| 接口 | 观测到的 query 参数（除 `sid`/`func` 外） |
| --- | --- |
| `mbox:getMessageData` | `mid`、`mode` |
| `oab:getHeadImageData` | `uid` |
| `oab:getCacheFile` | `lastCache` |
| 其余多数接口 | 仅 `sid` |

**精度上限（实测）**：不加行距限制时配对 7,451 条，但出现明显的**同线程污染**——
无关接口（如 `cim.user:getLunkrMailData`、`mbox:updateMessageInfos`）被套上了 `mbox:getAllFolders` 的文件夹列表响应形状。
收紧到 ≤4 行后降到 3,430 条，污染大幅减少但未完全消除。

**因此的采信规则**：02 的"响应结构"列**只采信**经独立验证或单一形状且无歧义的三个接口
（`mbox:getAllFolders`、`mbox:compose`、`upload:prepare`），其余一律标注"日志未可靠记录（见 04 §6）"，
**不把可能被污染的 JSON 形状写进交付物**。字段级 schema 仍需服务端契约验证或反编译（见 06 P1-2）。
