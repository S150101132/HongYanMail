# 搜索结果的时间按北京时间写（2026-11-08 修复）

**现象**：打开一封刚发出的回信，右上角显示 16:50，下面写「对方 11:50 发出 · 晚到 5 小时」。电脑和发信都是利雅得时间 11:50，16:50 是同一时刻的北京时间。刷新「已发送」后再打开，变回 11:50。

**原因**：所有 JSON-RPC 请求都带 `tz="Asia/Riyadh"`，服务器按利雅得时间写日期；只有搜索走网页表单接口 `XT/jsp/mail.jsp?func=searchMessages`，不带时区，日期按账号的 `time_zone`（本部署为 Asia/Shanghai）写。打开邮件时会按主题搜一遍同会话的邮件，把还没缓存的那封已发邮件连同北京时间一起写进缓存（问鸿雁的搜索也会这样）；之后文件夹列表刷新时才被正确时间覆盖。

**修复**：`CoremailAdapter.search_messages` 拿到结果后，把 `date` / `receivedDate` / `sentDate` 从账号时区换算到利雅得时间，和列表一致。账号时区用 `user:getAttrs` 的 `time_zone`（定时发送已在用，现在三处共用一个取法，只问一次）；没有固定偏移的时区不换算，搜索照常可用。已经存错的那几封，文件夹刷新后会自动改对。

## 验证

- 回归测试 `tests/test_desktop_search_move.py::test_search_dates_are_riyadh_time_like_the_list`：搜索返回北京时间 16:50:12，修复前得到 16:50:12（红），修复后得到 11:50:12（绿）；账号时区只问一次。
- 全量 `unittest`：893 个通过（11 个跳过）。
- 真实账号：用户刷新「已发送」后看到时间变回 11:50，符合上述原因。只读探测 `tools/probes/probe_search_date_zone.py`（对比列表和搜索的小时差，并试表单接口带 tz 是否有效）没有跑出结果：第一次脚本解析有误，第二次服务器要求人工验证登录。所以「表单接口能否直接带 tz」仍未验证，本次修复不依赖它。
