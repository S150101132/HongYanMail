# 邮箱可用性审查与改进范围

日期：2026-10-16。本文保留修改前的基线审查发现；用户确认后的修复与验证见 [本轮可用性进展](2026-10-16-usability-progress.md)。下文描述的是修改前状态。

## 本次实测

- 执行 `.venv\Scripts\python.exe -u -m unittest discover -s tests -v`。
- 154 项测试，152 项通过、2 项跳过、0 失败、0 错误，耗时 11.043 秒。
- 两项跳过均因本地 OpenSSL 无法构造 RC2 测试信封。
- 需要放宽执行沙箱才能启动项目 Python 和 Qt 子进程。
- 本轮没有登录真实邮箱，没有发送、移动或删除邮件。上述结果仅为现有自动化回归基线。

## 源码审查发现

1. 正文查找未接到真实阅读控件：`MainWindow.find_body` 查找 `view`，而 `ReaderView` 暴露的是 `web_view` 和 `fallback`。产品阅读器本身不提供 `findText` 或 `find`。
2. 切换文件夹和选择另一封邮件只清除正文与 document，没有同时清除旧的主题、头部或附件区域。慢请求或失败期间可能混合展示两封邮件的信息。
3. 所有视图请求共享 `generation`。选择邮件增加代次后，尚未完成的列表刷新或分页结果会被丢弃。需要按文件夹列表与当前正文分别判断结果是否过期。
4. 刷新和分页没有请求中禁用或重复请求保护，同一偏移可以重复提交。
5. `pending` 在登录完成前保存了包含 password 的参数字典；应只保留结果处理需要的非敏感上下文。
6. 邮件列表把发件人、日期、主题放入多行 DisplayRole 字符串，没有独立排版和截断规则。狭窄窗口下的信息层级与可读性需要视觉验证。
7. 回复能力被适配器明确关闭；附件仅提供描述，写信没有上传附件入口。现有测试中的“被阻止”通过不代表这些基础功能已可用。
8. 草稿恢复列表展示内部 ID，不能帮助用户按主题和时间寻找草稿。
9. README 的测试基线和验收状态与后续提交不同，应以本次执行及逐项真实验证更新。

## 建议实施顺序

### 补充：合成数据运行复现

在 offscreen Qt 窗口中注入只记录请求的 Controller 和 QTextBrowser，不联网、不读取真实邮件：

- 切换文件夹后，上一封邮件的主题、头部、附件文本全部仍在：已复现。
- 提交当前文件夹刷新后选择邮件，再返回刷新结果，合法列表结果被丢弃：已复现。
- 连续调用两次加载更多，会排队两个相同分页请求：已复现。
- 提交含合成占位 password 的登录请求后，UI pending 字典仍持有 password 字段：已复现；未使用或输出真实凭据。

上述复现说明，现有 154 项回归通过仍不足以证明完整日常操作可用。修复时应把这些场景纳入回归。

### 与原客户端的证据边界

已复核 `analysis/客户端整体结构梳理.md` 和 `analysis/protocol-feasibility.md`。原客户端阅读、附件、写信、快速回复等入口已有静态证据；其中 `attachmentDownload`、`sendcompose` 等属于客户端内部桥接命令，不是可直接照搬的服务器接口。后续实现应从已验证 transport 扩展，不能把桥接命令名直接当作 HTTP 路由。

第一阶段沿用当前 Qt 三栏架构和既有浅色/深色设计，完成现有交互修复与视觉优化：登录卡片、简化工具栏、清晰的文件夹选中态、分层邮件列表、阅读标题和附件区、统一状态提示；修复查找、过期结果、残留内容和重复加载；增加相关回归与窗口尺寸截图检查。

第二阶段参考原 Core Mail 的现有证据，逐项补齐回复/回复全部、附件保存/上传、已读未读、移动/删除和搜索。涉及新的服务端操作时先明确实际协议与成功条件，失败必须可恢复；发送结果不明不得自动重发。

验收以用户任务为单位：登录后选择文件夹、分页与筛选、快速切换邮件、阅读普通及已支持的加密邮件、查找正文、保存并恢复草稿、发送及确认结果、处理附件；同时覆盖断网、会话失效、关闭窗口、浅色/深色和最小窗口。

真实收发、附件和服务端状态变更应单独记录验证范围与结果。原客户端和现有账号数据不应因开发验证而改写。
