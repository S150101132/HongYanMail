## 2. 自动化回归

```powershell

```

结果：**126 项通过，0 失败，0 错误**，耗时 7.9 秒（`analysis/unittest-result.json`）。

执行环境说明：Qt WebEngine 的渲染子进程无法在 DSH 文件沙箱内创建（Chromium 报 `Check failed: 拒绝访问 (0x5)`），因此真实渲染器阅读测试需要在放宽沙箱下运行。测试模块自身会声明所需环境（offscreen 平台与测试驱动器的 `QTWEBENGINE_DISABLE_SANDBOX=1`）；产品本身从不关闭 Chromium 自带沙箱。

本轮新增或修正的测试：

- `tests/test_desktop_messages.py`：每个可由代码抛出的错误码都必须有固定安全文案；异常自带的 URL、sid、密码、收件人不得进入界面文案。
- `tests/test_desktop_acceptance.py`：离线启动、最小窗口 1000×680、基准 1280×800、快捷键不冲突、1000 条列表的视图模型、筛选只声明“已加载”范围、登录可仅用键盘完成（含回车提交）、加密发送阻止提示不会被自动保存状态覆盖、未保存退出保护、会话失效后编辑内容保留、Unknown 结果不可重试、多次会话失效只提示一次。
- `tests/test_coremail_transport.py`：改用 `tests/fixtures/login/public-login-form.html` 合成样本，不再依赖被忽略的研究产物。
- `tests/test_desktop_reader.py`：改为断言真实可读的 DOM 文本。原先断言 `loadFinished` 的布尔值为真，但正文中被正确阻止的远程图片会让 Chromium 报告加载失败，因此该断言衡量的是错误的东西。

### 协议适配器的端到端验证（本地 HTTPS）

`tests/test_desktop_adapter_integration.py` 首次让生产适配器面对真实的 HTTP 端点：它用一个本地 TLS 服务器（自签测试证书 + 注入信任该证书的 opener）跑完登录表单解析、同源跳转、Cookie 传递、ExtendedJSON 解码、错误分类、有界重试与 MIME 获取。全程合成数据，只用 `127.0.0.1`。

10 项断言覆盖：

| 行为 | 结论 |
| --- | --- |
| 登录先解析公开表单，再调用已认证接口 | 通过；只拿到 sid 不算登录成功 |
| 文件夹与分页摘要映射为类型化模型 | 通过，角色识别为 inbox/sent |
| `fetch_mime` 返回原始 RFC 5322 报文 | 通过 |
| `continue` 建会话 → `deliver` 提交 | 通过 |
| 回复引用头在契约验证前被拒绝 | `REPLY_CONTRACT_UNVERIFIED` |
| 要求加密的草稿不会走普通提交 | `ENCRYPTED_SUBMISSION_UNVERIFIED` |
| 会话失效只提交一次、不重试 | 通过 |
| 只读请求在有界重试内恢复瞬时 500 | 通过 |
| 写操作只提交一次 | 通过 |
| 超过 64 MiB 的响应被拒绝 | `RESPONSE_TOO_LARGE` |
| 跨来源请求在发出前被拒绝 | `UNSAFE_ORIGIN` |
| 系统不信任的证书导致 TLS 失败而非继续 | `TLS_ERROR` |

必须强调：这些是**传输与状态机行为**的证据，不是公司服务器兼容性证据。真实 origin、真实 TLS 链、设备校验、`csm` 企业封装与加密提交契约仍然未验证。

### 加密存储与发送记录的抗故障验证

`tests/test_desktop_storage_torture.py` 针对草稿存储与发送记录做故障注入，验证设计稿第 9 节与 Review Focus 第 5 项要求的属性：

| 场景 | 结论 |
| --- | --- |
| 20 轮随机中断写入（`os.replace` 失败） | 已提交修订永不丢失或损坏；失败写入不改变可读修订 |
| 每轮全盘扫描明文 | 主题、正文、收件人从未以明文落盘 |
| 中断后临时文件 | 不残留任何 `.tmp` 文件 |
| 重开存储 | 恢复最后成功提交的修订 |
| 记录被截断（模拟撕裂写入） | 明确报错，不静默当作成功；恢复原文件后仍可读 |
| 旧修订回写 | 被拒绝，不覆盖较新内容 |
| `Submitting` / `Reconciling` 重启 | 一律转为 `Unknown`，冻结载荷保留，绝不自动重发 |
| `Preparing` 重启 | 转为 `Failed`（提交前状态，可由用户明确重试，不应谎报为结果不明） |
| 状态写入失败 | 不抹掉上一条权威记录，且不残留临时文件 |

其中 `Preparing → Failed` 与 `Submitting → Unknown` 的区别是本轮明确的语义：发送前失败是可确定的失败，只有可能已到达服务器的状态才必须保持“结果待确认”。

### 体积裁剪

初版打包为 573.7 MB。裁剪不是按猜测删文件，而是用 `packaging/bisect_qt_dlls.py` 在已知可用的包上逐个删除候选文件并重新运行诊断入口，只保留被证明“删掉仍可用”的部分，结果存于 `analysis/bundle-trim-experiment.json`。

- 已证明可删除 55 个文件（Qt Charts / DataVisualization / Graphs / Quick3D / Labs / Multimedia / Pdf / VirtualKeyboard / ShaderTools / SQL / Test / Sensors / SerialPort / WebSockets / RemoteObjects / Scxml / OpenGLWidgets、`opengl32sw.dll`、`QtOpenGL.pyd`、`QtQuickWidgets.pyd`）以及 Qt 翻译目录。
- 已证明**必须保留** `Qt6OpenGL.dll`：没有任何代码直接引用它，但删掉后 `QtWebEngineCore` 会以 `DLL load failed` 失败。这一条曾被错误的“只看进程是否存活”判据漏掉，原因是打包后的窗口程序在导入失败时会弹异常对话框而进程仍存活；现在的判据由带日志的控制台诊断入口给出。
- 结果：450.3 MB，比初版减少 123.4 MB。

体积仍有近半来自 `Qt6WebEngineCore.dll`（194 MB），它是正文隔离阅读的必需组件；本轮不承诺更小体积。

## 5. 性能基线（首次实测）

设计稿第 14.2 节要求先测量再谈预算。下表是单机实测值（offscreen 平台、合成数据），用于建立基线，**不是预算承诺，也不是干净用户环境的数值**。原始数据见 `analysis/performance-baseline.json` 与 `analysis/runtime-baseline.json`。

| 项目 | 实测中位数 | 说明 |
| --- | --- | --- |
| 解析 58 KiB 合成 MIME | 32.9 ms | 在后台 worker 线程执行，不占用 UI 线程 |
| 解析 956 KiB 合成 MIME（含 5 个附件） | 592.9 ms | 同上；这是首次打开大邮件的主要成本 |
| HTML 净化 120 KiB | 212.6 ms | bleach 白名单，同样在 worker 线程 |
| 合并 1000 条摘要 | 0.07 ms | 每页 50 条的合并开销可忽略 |
| 列表装入 1000 行 | 1.46 ms | QListView + 单一模型，不为每封邮件建控件 |
| 在 1000 行中筛选 | 1.52 ms | 满足“100 ms 内给出视觉反馈” |
| 写入 50 个 CID 资源 | 0.01 ms | 仅内存，成功后才替换当前文档资源 |
| ReaderView 构造（含 WebEngine profile） | 254.1 ms | 一次性成本，不是每封邮件的成本 |
| 打包产物启动到内存稳定 | 约 5.7 s | 近似值：工作集连续三次采样不再增长；不是首帧时间 |
| 打包产物空闲工作集 | 146.6 MB | 仅主进程；WebEngine 渲染进程按需启动 |
| 打包产物空闲私有内存 | 80.8 MB | 同上 |

关键结论与边界：

- **UI 主线程不等待网络或解析**：解析、净化与证书操作都在账号 worker 线程执行，这一点由架构测试证明，不由上表数值证明。
- **空闲时不启动渲染进程**：实测打包产物静置 12 秒后没有任何 Qt WebEngine 子进程，正文第一次渲染时才派生；这意味着空闲内存测量不含渲染进程。
- **尚未测量**：真实服务器延迟与首封正文耗时、干净 Windows 用户环境的冷启动、打包产物中真实邮件的 HTML 渲染耗时。上表不能替代这些。

## 7. 已知限制

1. 真实独立登录、真实读取与自发自收仍需本机交互执行；证书解锁与真实加密邮件格式已完成实测。
2. **加密邮件解密目前不可用**：真实邮件的内容加密为 3DES-CBC，当前 pyca/cryptography 高层 pkcs7 接口只接受 AES-CBC，因此不支持 3DES。已实测该能力可达（系统 OpenSSL 3.5.7 成功解密真实邮件），可行修复方案见 `analysis/certificate-compatibility.md` 第 5 节。因此 V0.1 **不能**声称已支持加密阅读。
3. 加密邮件的网络提交契约未验证，因此加密发送被显式阻止，且不会降级为明文。
4. 回复与回复全部入口保持禁用，直到引用头契约验证通过。
5. 不提供附件上传/下载/预览、已读回写、移动删除、服务端搜索、多账号、富文本。
6. 长时间运行（10 分钟无泄漏迹象）与 100–200% 缩放几何已验证；但 125–200% 缩放的真实显示器目视验收、标签文字裁切检查仍属未做。内存与启动为单机基线，不是干净用户环境数值。
7. “干净用户环境”验收由本机进程级检查近似（中性工作目录启动、无开发环境依赖），不等于在另一台未安装开发工具的机器上人工验收。

## 8. 下一轮建议顺序

1. 完成一次真实交互登录与只读浏览，记录覆盖范围。
2. 按兼容性报告第 5 节实现 CMS 3DES 解密（优先进程内方案），再用真实加密邮件与原客户端双向复核，然后才解除加密阅读与加密发送的阻止。
3. 在可控收件人下完成一次真实新信发送与收件箱 MIME 核对，验证 Unknown 恢复路径。
4. 取得回复引用头与加密提交契约的真实证据后再启用对应入口。
