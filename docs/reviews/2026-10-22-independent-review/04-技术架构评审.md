# 技术架构评审

## 总体判断

鸿雁具备可复用的邮件客户端底座，不建议全面重写。Python + PySide6/QWebEngine 宿主、HTML/CSS/JavaScript 界面、QWebChannel 桥接、无 Qt 后端、Coremail HTTPS 适配器已经形成清晰的初始分层。但产品扩展速度超过了应用服务层的拆分速度：单个 MailBackend 已超过 4,000 行，混合邮件、任务、归档、AI、项目记忆与个人关系逻辑。下一阶段主要矛盾不是技术栈落后，而是可靠性边界、数据权威性和规模边界不够明确。

## 真实架构与数据流

- 入口：`pyproject.toml` 注册 `coremail_desktop.bootstrap:main`，运行依赖包括 PySide6、cryptography、bleach、zstandard。生产不是标准 IMAP/SMTP 客户端；`protocol/coremail.py:12` 引用 `probe.coremail_transport`，通过 Coremail HTTPS 接口读写邮件。
- 界面：`app/web/` 多份原生 JS 按任务、邮件、联系人等拆分，`app/shell.py:260` 起的 Bridge 接收白名单调用，后台结果通过 Qt 信号返回。
- 并发：`app/shell.py:273` 起设置邮件、快速查询、预取、AI、归档、任务六个单线程执行器；避免把常规网络工作直接放到 UI 线程，但多个执行器仍共享同一个 Backend。不能把“每池单线程”理解为“全应用业务串行”。
- 邮件数据：`app/cache.py:28` 起使用 SQLite WAL、AES-GCM，每账户密钥由 Windows 当前用户 DPAPI 封装；全部摘要启动时解密进内存，正文缓存预算 300 MiB。邮件 ID、文件夹 ID、时间戳等索引元数据仍是明文，因此不是整个数据库全字段加密。
- 本地正式记录：`tasks/store.py:35` 起保存任务、修订号、事件、关联，使用 FULL 同步并拒绝在已有库缺密钥时新建密钥；这类记录不能当邮件缓存随意清除。
- AI 派生记录：`memory/store.py:31` 起保存理解卡、规则、事实；项目键使用 HMAC，但事实状态与时间可见。
- 发送：`outbox/service.py:17` 起先落发送意图，再构建提交，进入 Submitting 后才调用网络；接受结果丢失转 Unknown，不盲目重发。`outbox/journal.py:19` 将恢复中的 Submitting/Reconciling 转 Unknown。这是应保留的核心资产。

## 安全与可靠性已有优点及边界

1. `storage/dpapi.py:13` 无明文 fallback，保护失败报固定错误。DPAPI 是当前 Windows 用户边界，不能抵御同用户恶意进程，也不自动支持换机恢复。备份必须包含正式记录与可恢复密钥方案，不能只拷数据库。
2. `ai/client.py:25` 只允许 HTTPS；`:48` 禁重定向避免 API key 转发；错误转换成固定代码；响应大小有限制。它证明传输防护存在，不证明企业允许把邮件送到该 endpoint。
3. `shell.py:200–219` 远程图片默认受拦截控制，邮件渲染另有隔离和 sanitization；用户允许图片仍可能产生跟踪请求，应保持按邮件授权语义。
4. `outbox/service.py` 的 Unknown 状态设计合理：不能以网络超时直接提示“发送失败，可重试”。必须在 UI 保持“结果待确认”，并提供查已发送与人工确认路径。无服务端关联 ID，客户端无法保证端到端 exactly-once。
5. `ai/client.py:145` 流式取消在读取片段之间检查；阻塞读取期间取消不是立即中止。单 AI 执行器下可能影响后续请求，需加入请求超时预算与可终止连接，验收应包含服务器不返回片段。

## 支持 AI 的演进方式

沿现有模块渐进提取 `MailService / SendService / TaskService / MemoryService / AIOrchestrator`。UI 发出意图，应用服务负责权限和事务，协议只负责 Coremail 语义，模型只返回候选理解与表达。发送、移动、任务更新仍走普通业务命令和原来的状态机。

统一 AI 请求信封：账户/会话代次、允许的邮件 ID、用途、数据分类、模型 endpoint、输入内容哈希、策略版本。输出保存来源邮件及片段定位、模型/提示版本、生成时间、确认状态；模型输出不能扩大读取范围或直接调用发送。

加入一个可暂停的后台作业调度层，区分用户即时读信、发送、后台预取和 AI；为每类工作设并发、队列上限、重试与取消规则。当前六个线程池可作为过渡实现，无须立刻引入独立服务或复杂消息队列。
