# UX/UI 专项评审

日期：2026-10-22。证据为当前 HTML/CSS/JavaScript 与后端。合成演示截图尝试未成功（本地测试目录 account.bin 写入权限错误），没有真实界面走查；本文所有点击数都是静态推导的路径下界，不含输入、等待、配置和异常处理，不是用户实测。视觉层次、字体清晰度、缩放、窗口压缩、实际响应时间均待验证。

## 核心判断

三栏阅读与就地任务卡片方向合理，已存在精简工具栏、统一助理、今天页等收敛工作，不能把历史“六个 AI 入口”直接当作当前问题。当前更值得关注的是状态语义和覆盖边界，而非再换一套布局。

## 八个完整场景

| 场景 | 当前路径与证据 | 主要负担/风险 | 推荐路径及验收 |
|---|---|---|---|
| 首次打开 | 默认今天 → 点条目 → 阅读/任务卡；today.js enterApp，backend.today_overview | AI 未开启、尚未理解、无日期任务不进入主清单；空态仍说“今天没有要你做的事” | 首页显示“已识别待办”与覆盖提示，直接进入未检查收件箱；未完成理解时不得宣称无待办 |
| 新邮件与往来 | 点邮件1次；展开会话再选历史邮件额外2次；app.js:492、576 | 子邮件在列表展开，阅读单封时需跨区选择；主题分组可能混入同名事项 | 阅读区顶部显示会话成员与来源，下一封连续切换；合成同主题不同事项不得无提示合并 |
| 找历史决定/附件 | 输入本地结果 → 回车服务器 → 点结果；app.js:690–733 | 输入与回车覆盖不同范围；“没找到”可能误解成不存在 | 常驻“本机/服务器/存档”范围与搜索进度；离线明确仅缓存，返回结果保留查询与位置 |
| 写信/回复/收件人组 | 写信或回复 → 收件人组 → 选组，填充后核对；groups.js groupMenu/applyGroup | 菜单仅取前15组，没有菜单内检索；第16组需管理等间接路径 | 菜单搜索全部组，常用置顶；填充后展示主送/抄送及新增外部地址；不自动发送 |
| 未来跟进 | 阅读 → 转任务/任务操作 → 日期；本次未见独立轻量邮件稍后提醒入口 | 一封简单跟进可能承担任务中心导入和字段概念 | 阅读处“提醒我”→ 日期（约2次选择），持久化提醒但不归档邮件；关闭应用再开仍存在 |
| 多邮件多人同一事项 | 邮件关联任务 → 任务详情 → 关联邮件；tasks.js 与 memory.js | 邮件会话、项目记忆、任务有不同身份，AI 错关联需要追溯 | 一个事项卡包含下一步、负责人、日期、来源邮件；关系允许删除，跨项目不自动写进展 |
| 久未处理重新进入 | 任务 → 最新进展/历史；项目记忆 → 相关事实 → 原邮件 | 用户要区分当前结论、旧事实和 AI 推断 | 摘要只呈现当前状态、最后决定、下一步，逐条来源/日期；冲突并列而非覆盖 |
| 邮件量多避免淹没 | 收件箱未读/星标/要我做筛选；今天按到期排序 | 无日期行动排后、未识别邮件不在今天，数量不代表业务重要性 | 保留未检查队列和用户置顶；批量处理可撤销；用户纠正优先于自动分类 |

“提醒我”是建议的新轻量交互，不声称当前已实现；应先验证频率，再决定是否值得增加。

## 重要问题与前后路径

### P0：回复行为不能替代业务完成

事实：backend.py:3723 understand_answered 在回复/转发成功后，将会话中更早且 sure 的卡片设为已处理。其判断依据是邮件时间与会话关系，不是业务承诺是否完成。推断：回复“明天处理”或转发给同事可能让仍需跟进的事项退出行动列表。

当前：回复/转发 → 发送 → 自动已处理 → 必须发现提示并撤销。
建议：回复 → 发送 → 显示已回复，事项保持原状态；仅用户点“已完成”关闭，或给一次非阻断建议。验收包括“收到”“需补资料”“转交协助”“任务已完成”四种邮件，不自动把前三类完成。工作量中，依赖邮件状态与工作状态分离，风险是行动列表变长，需要同时提供批量明确处理。

### P0：今天空态表达超出实际覆盖

事实：today.js tdRender 使用“今天没有要你做的事”；backend.today_overview 只取启用理解层的 act 邮件与近三天到期非受阻任务。无日期任务、未理解邮件不代表不存在。

当前：开机 → 空清单 → 用户自行记住去收件箱核查。
建议：开机 → “已识别待办 0；仍有邮件未检查/理解未开启” → 一键收件箱；无可靠覆盖统计时只说“此视图暂无条目”。工作量小至中；验收覆盖未配置 AI、理解失败、无日期任务、离线四种状态，不出现全局无事可做的断言。

### P1：混排清单的键盘选择模型不统一

事实：today.js tdRender 将 S.items 从 S.rows 映射生成，而任务卡片另用 data-task 与 tdShowTask；通用邮件键盘逻辑使用 S.items。推断：混排任务无法完整复用邮件 J/K 路径，需要运行确认，不能断言所有键盘操作已坏。

建议：统一选择项为 kind/id，导航只移动焦点，执行动作按类型分派。验收鼠标与键盘均能按显示顺序遍历每个邮件和任务，无跳过/焦点丢失；工作量中，依赖共享选择模型。

### P1：搜索范围与组菜单的隐性规则

当前搜索“输入即本地、回车全量”的提示已经存在（app.js:733），不能说完全没有反馈；问题是其可见性和用户是否读到待验证。收件人组前15条截断则是明确代码事实（groups.js groupMenu）。

建议：搜索范围常驻而非只放结果副标题；组菜单显示全部可检索，不让管理页承担选择工作。验收16组和100组均可按名字找到；离线结果显示来源，网络失败不清掉已有结果。工作量小。

### P1：任务上手包含过多存储概念

事实：index.html:421–431、tasks.js:63 要求设置任务文件夹、检查导入两份工作簿、演练转正式、导出；这是明确的特定工作表迁移流程。

当前：任务 → 设置 → 目录 → 导入 → 演练 → 正式。
建议：新用户直接建立个人事项；既有 Excel 用户走单独导入流程，导出与冲突状态保留在可展开详情。不能删除现有迁移能力。工作量中至大，依赖任务存储初始化与迁移兼容；验收不准备工作簿也能建首条事项，原用户导入/恢复无损。

## 信息架构草案

左侧：写邮件；收件箱；今天（可选首页）；事项；文件夹（折叠）；通讯录。发件箱异常常驻提示，正常时可收起；本机与服务器草稿统一入口带来源标签。中间为同一列表；右侧为邮件或事项详情；助理按需打开，明确当前上下文和将读取的来源。

项目是事项和邮件的筛选属性。甘特图与 Excel 兼容置于事项高级视图，不进入初次上手。不是要求立即删除已实现功能，而是减少默认用户必须理解的概念。

## 视觉、状态与可访问性验证清单

CSS:110 三栏使用固定侧栏默认232px、列表默认400px和剩余阅读区；这是布局意图，不足以证明小屏可用。需在1280×720、1920×1080、125%/150%缩放和助理打开状态，检查正文宽度、工具栏溢出、长主题与中文换行。列表主信息应限于人物、主题、时间、未读/附件与一个行动标记；以实际截图检查 AI 文案是否挤占主题。

现有加载骨架、加载更多失败重试、离线缓存条（app.js:439、585、1948）、草稿失败提示、发送不明路径应保留。测试要确认“正在发送/已提交/待确认/失败”能被理解，不把固定错误码脱敏等同于信息充分。

index.html 存在没有 href 的导航 a 元素；鼠标事件不保证可键盘聚焦。建议逐个验证 Tab 顺序、焦点环、弹窗关闭后焦点恢复、屏幕阅读器名称和状态播报。为导航补正确链接/按钮语义，避免只靠颜色表示未读/逾期。工作量中；验收不使用鼠标完成阅读、回复、选组、搜索、取消与设置。

## 试用判定

不要以“页面能打开”验收体验。五个工作日记录八场景的完成率、来回切换次数、等待感知、错误纠正、漏办及信任下降原因。点击数降低但核对负担增加不算改进；自动分类准确率必须同时统计漏掉的重要邮件，不能只统计已展示卡片的正确率。
