# 鸿雁 AI 原生邮箱产品设计方案 V1.0

> **定位**：产品方案 / 设计基线（非开发授权）  
> **版本**：V1.0 · 2026-10-22  
> **状态**：产品方向已讨论形成共识；细节含待确认假设；尚未批准修改正式开发路线图  
> **适用范围**：鸿雁 Windows 桌面邮箱，当前主要针对 Coremail 企业邮箱场景  
> **设计目标**：简单易用、顺畅高效、智能自然、可靠可控  
> **重要说明**：本文整合产品负责人在对话中选择的方向与 Work 的九份独立评审材料。本文未再次打开项目源码、运行客户端或验证 GitHub 记忆框架；“现状”来自 2026-10-22 评审快照，“目标”是拟议设计，两者必须区分。

## 0. 执行摘要

**一句话定位**：鸿雁是一款以可靠邮件沟通为核心、以工作事项为连续上下文、以 AI 为自然辅助的个人工作邮箱。让用户少切换、少重复整理、不遗漏重要承诺，并始终能够核查依据、纠正错误、恢复工作。

### 0.1 已形成的产品方向

| 主题 | 目标方向 | 状态 |
|---|---|---|
| 首页 | **方案 C：融合式首页**，同时呈现邮件、已确认事项、等待反馈和 AI 候选 | 用户已明确选择；默认启用策略仍待试用验证 |
| 产品优先级 | 首先是可信、顺畅的邮箱，然后是围绕邮件工作的助手 | 已形成共识 |
| 导航 | 工作台 / 收件箱 / 事项共用阅读区与搜索；高级功能渐进展示 | 目标设计，未批准实施 |
| 邮件与工作 | 邮件通信状态和工作完成状态必须独立 | 已形成共识，P0 修正方向 |
| 事项详情 | 顶部展示下一步，内部有概览 / 关联邮件 / 工作记录 | 目标设计 |
| 智能关联 | 确定关系靠程序，候选关系靠 AI，正式关联可确认、可撤销 | 目标设计 |
| 工作记忆 | 正式事实与 AI 派生理解分层，保留来源、时间、版本与纠错 | 目标设计 |
| 主动性 | L0 静默 / L1 就地 / L2 工作台 / L3 通知；默认克制 | 目标设计 |
| AI 交互 | 就地按钮、上下文侧栏、Ctrl+K 共享同一助手能力 | 目标设计 |
| 技术方向 | 复用现有 Python/PySide6、JS 前端、正式任务库及记忆模块，渐进解耦 | 目标设计 |
| 外部记忆框架 | 可以研究 Mem0 / Hindsight，但**当前不做选型 PoC，也不绑定方案** | 当前明确暂缓 |

### 0.2 不变的底线

1. **没有 AI 也能完成完整邮箱工作**：收发、阅读、搜索、附件、草稿与手动跟进不依赖模型成功。
2. **回复不等于完成**：发送成功只证明沟通动作，不能直接关闭工作事项。
3. **AI 不得制造错误的安心感**：未分析、未同步或覆盖不足时，不允许称“没有待办”。
4. **用户掌握正式工作记录**：AI 推断默认是建议；日期、承诺、归属、完成状态等重要变更需可靠来源和确认机制。
5. **组织数据策略先于便利性**：不得因用户个人配置外部模型而绕过企业限制；授权撤销后必须阻止新的不合规出站。
6. **正式记录可恢复**：用户确认的事实、纠错、任务及关联，不能因为 AI 缓存损坏或密钥不可读而悄然丢失。

### 0.3 非目标（本阶段明确不做）

- 开发完整通用项目管理平台、多人实时权限协作或独立企业知识库。
- 让 AI 自主发送邮件、自动认定任务完成、自动变更关键交付承诺。
- 默认扫描和向量化整个历史邮箱、部署复杂知识图谱或多 Agent 自治平台。
- 因新增 AI 能力而重写全部客户端、复制邮件存储、另建第二套正式任务数据。
- 当前阶段进行 Mem0/Hindsight 集成验证或决定唯一技术供应商。

## 1. 用户、工作目标与产品成功定义

### 1.1 目标用户（初步定位，尚非用户研究结论）

首批核心场景是企业 Coremail 员工：邮件驱动跨人沟通，需要频繁查找历史上下文、跟进客户或同事的回应；部分用户也需要把现有 Excel 工作台账逐步迁移进客户端。后续是否推广到其他企业、账号体系或多人协作，需独立论证。

### 1.2 用户真正要完成的工作（Jobs to Be Done）

| 时刻 | 用户真实目标 | 鸿雁需要降低的成本 |
|---|---|---|
| 刚开始工作 | 快速了解邮件与工作中值得关注的部分 | 判断成本、遗漏风险 |
| 收到邮件 | 理解新要求、前因后果、是否需要回复 | 阅读成本、查找上下文成本 |
| 回复邮件 | 正确、及时地回复，必要时衔接后续行动 | 重复输入、反复切换 |
| 持续协作 | 记住已经承诺什么、谁还在等谁、后来发生了什么 | 记忆和维护成本 |
| 重新接手旧事项 | 找回最新状态、历史决定和原始证据 | 检索成本、误用旧事实风险 |
| 工作结束 | 可靠地知道仍需处理、需要等待及何时提醒 | 漏办和错误完成风险 |

### 1.3 四组产品原则

- **简单**：高频动作就地完成；不为一封简单邮件强制创建复杂任务；逐步展示高级功能。
- **顺畅**：统一列表与详情区域；切换视图保留选择、滚动、搜索范围和草稿上下文；避免加载阻塞。
- **智能**：优先自动理解、提供证据和建议，而非增加聊天层级；AI 主动思考、克制表达。
- **可信**：来源可追、覆盖可知、状态可改、操作可撤销、数据可恢复；宁可说“不确定”，不捏造确定结论。

### 1.4 成功指标（先建立基线，不编造目标值）

核心关注：首次启动到定位首项工作的时间、八个高频场景成功率、每次完成工作的页面切换、误完成与漏办事件、建议纠正率、关联误判/漏判、找到原邮件依据成功率、发送未知状态的正确恢复、五日试用的主观信任与返工情况。AI 生成次数与功能数量不是成功指标。

## 2. 当前产品事实及设计约束

本节是**来自已上传评审的快照**，不是本文件重新执行的源代码验收。

### 2.1 已核实或已有实现路径

| 领域 | 当前评审中确认的证据 | V1.0 处理方式 |
|---|---|---|
| 桌面底座 | Python + PySide6/QWebEngine；HTML/CSS/JS；QWebChannel；Coremail HTTPS 适配 | 原则上复用，不整体重写 |
| 邮件列表、分页、搜索、会话、草稿和发送 | `coremail_desktop/app/web/app.js`、`index.html`、`outbox/` | 完整保留并优先验证可靠性 |
| 固定收件人群组 | `app/web/groups.js` 的主送/抄送填充、去重 | 保留；改进大量群组的搜索发现 |
| 今天页 | `app/web/today.js` 与 `app/backend.py:today_overview` | 作为融合首页演进基础，而非复制一套页面 |
| 任务中心、Excel 迁移 | `app/web/tasks.js`、`tasks/store.py` | 保留正式任务能力；Excel 作为兼容/迁移路径，单一权威源待决定 |
| AI 理解和候选关联 | `ai/understand.py`、`app/web/understand.js` | 复用为候选生产者，增加证据和确认边界 |
| AI 问答、写作 | `ai/agent.py`、`ai/tools.py`、`ai/writing.py` 等 | 统一上下文与授权，不另建一套聊天系统 |
| AI 记忆 | `memory/store.py`、`memory/merge.py` | 保留可复用能力，强化冲突、来源、密钥恢复 |
| 发送结果不明 | `outbox/service.py` 的 `Unknown` 状态与恢复日志 | 明确保留，绝不因超时盲重发 |

### 2.2 评审已发现的风险/问题

| 编号 | 类别 | 问题 | 证据性质 |
|---|---|---|---|
| E-01 | P0 | 回复/转发后可能把早期理解卡标成“已处理”，并不代表业务完成 | 源码行为确认；影响程度待场景验证 |
| E-02 | P0 | “今天没有要你做的事”超出当前 AI/任务汇总的实际覆盖范围 | 源码确认；真实窗口观察到该空态 |
| E-03 | P0 | AI 引用存在性不等于语义有依据，缺失 `sure` 可能被当成确定 | 源码分析风险 |
| E-04 | P0 | `memory/store.py` 缺密钥或解密失败可能被表现为无记忆 | 源码分析风险 |
| E-05 | P1 | 从「今天 → 在等别人」输入本机搜索词，标题变搜索结果，列表仍是旧内容 | 真实窗口已复现 |
| E-06 | P1 | 混排列表的邮件和任务选择模型不同，键盘遍历可能不一致 | 源码推断，未完成运行验证 |
| E-07 | P1 | 本机搜索与服务器搜索覆盖范围不同，用户可能误解“找不到” | 代码存在提示；可见性需要验证 |
| E-08 | P2 | 约 1274×720 窗口下部分标题被截断，部分工具栏不按对象适配 | 真实窗口观察 |
| E-09 | 待验证 | 打开任务详情可能触发模型请求及标题写入；阅读邮件可能自动标记已读 | 源码指出潜在副作用，真实路径未测 |
| E-10 | 待验证 | 真实发送、离线恢复、附件、AI 质量及完整同步 | 现有只读验证没有覆盖，不能宣称通过 |

**解释纪律**：在文档和开发任务中必须保留“已复现”“源码风险”“设计建议”“待验证”的区分，不把风险写成已发生事故。

## 3. 产品概念与信息架构

### 3.1 核心对象及边界

| 对象 | 职责 | 不能误当成什么 |
|---|---|---|
| Mail | 实际收发邮件与原始沟通证据 | 不能自动等同一项工作 |
| Thread | 具有真实通信关系的一组邮件 | 不能自动等同同一工作事项 |
| Work Item（工作事项） | 有目标、下一步、状态和生命周期的工作 | 不复制邮件实体，不等于 AI 候选 |
| Follow-up（轻量跟进） | 邮件或事项上的待提醒/等待约定 | 不强制升级成多步骤任务 |
| Link（关联） | Mail/Thread 与 Work Item 的有来源关系 | 不能仅凭主题相同而确定 |
| Memory Fact（事实记忆） | 有来源、有效时间和确认状态的事实 | 不能把生成摘要当正式决策 |
| Suggestion（建议） | AI 派生、可采纳/忽略/否定的候选行动 | 不能直接修改正式状态 |
| AI Context（上下文） | 本次用户操作允许 AI 读取的对象与范围 | 不能用当前选中对象推定全邮箱权限 |
| Attention Event（关注事件） | 决定某个候选应该静默、就地、工作台或通知 | 不能替代原始邮件通知机制 |

### 3.2 一级导航

- **工作台**：融合式首页，展示当前工作优先队列、未检查新邮件、等待反馈及少量 AI 建议。
- **收件箱**：原始邮件的完整工作入口，保留文件夹、未读/星标/搜索、会话阅读、写信与附件。
- **事项**：正式任务/跟进及高级事项管理（Excel 兼容、甘特等放入高级入口）。
- **文件夹 / 草稿 / 发件 / 通讯录**：保留标准邮箱基础结构；异常发送状态入口应可发现。
- **AI 助手**：不是新的顶层业务数据仓库；按上下文就地出现、侧栏展开或 Ctrl+K 调用。

导航标签「工作台」是目标称谓，不能把已实现的「今天」页面的覆盖范围当成完成版工作台。

### 3.3 主窗口布局

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 鸿雁  [全局搜索：本机 / 服务器 / 存档范围]            [写邮件] [AI]      │
├──────────────┬───────────────────────┬───────────────────────────────────┤
│ 左：导航     │ 中：统一工作流列表    │ 右：内容与操作                    │
│              │                       │                                   │
│ 工作台       │ 需要我处理            │ 邮件原文 / 会话                    │
│ 收件箱       │ 新邮件/待检查         │ 或工作事项的下一步、进展、来源    │
│ 事项         │ 在等别人              │ 或草稿编辑                        │
│ 文件夹       │ AI 候选（少量）       │                                   │
│ 通讯录       │                       │ AI 侧栏按需替换/扩展上下文空间    │
├──────────────┴───────────────────────┴───────────────────────────────────┤
│ 同步与覆盖状态 / 发送异常 / AI 授权状态（按需显示）                      │
└──────────────────────────────────────────────────────────────────────────┘
```

- 中间列表与右侧阅读区尽量复用，不通过跳新页面完成高频邮件动作。
- 1280×720 和系统 125%/150% 缩放下，应保留可辨页面标题，允许收起导航，防止 AI 侧栏挤压正文。
- 每类对象声明其可用工具栏操作；不要让本机草稿、发件箱等无差别继承所有收件箱筛选。
- 键盘、鼠标、焦点与筛选/滚动状态使用统一选择模型。

### 3.4 首页默认策略的区分

- **产品方向已决定**：目标是融合式首页（方案 C）。
- **上线/迁移策略暂不直接决定**：现有用户可以选择/记住首页偏好；新用户、AI 未就绪或覆盖不足时，不应强制一个看似完整的 AI 清单。具体默认入口需五日试用与可靠性门槛后确认。

## 4. 融合式首页详细规范

### 4.1 四个区块与展示顺序

| 区块 | 纳入原则 | 默认操作 | 特别边界 |
|---|---|---|---|
| 需要我处理 | 用户确认的未完成事项、到期/置顶工作、可核实的待行动信息 | 打开事项、继续处理、标记完成 | AI 候选不假冒正式待办；邮件回复不触发自动完成 |
| 尚未检查的新邮件 | 用户尚未阅读或检查的原始邮件 | 阅读、回复、跟进、归档 | 原邮件完整保留；AI 未分析不代表不重要 |
| 在等别人 | 用户设定的等待/到期，或标清为候选的催办事项 | 查看邮件、修改等待时间、生成催办草稿 | 对方部分回复≠全部完成；无回复的判断范围可见 |
| AI 建议 | 新要求、日期冲突、候选关联、可能跟进，按价值精选 | 查看依据、确认、稍后、忽略 | 不作为必须清空的第二个收件箱 |

### 4.2 去重与聚合

- 一项已确认工作可以聚合多封关联邮件；在首页形成一个工作入口，显示新邮件数/最新变化。
- 不应生成“任务 + 多条 AI 建议 + 多份提醒”的重复工作入口。
- 聚合只影响工作台展示，不删除、隐藏或改变完整收件箱中的原始邮件及未读状态。
- AI 尚未确认的跨会话关联不得强行合并进正式事项；可用简短候选标识。
- 同一封邮件可以涉及多个事项，但每项正式关联应有独立、可撤销记录。

### 4.3 空态和覆盖说明

允许的文案：**“当前工作台暂无已识别事项；仍可查看完整收件箱。”**

不允许的文案：**“今天没有要你做的事”**（除非未来真的有可靠的全覆盖定义和证据）。

建议状态字段：最近邮件同步时间、邮件缓存覆盖范围、已分析/待分析/失败数量、AI 未开启或授权受限状态、未设日期事项的可见入口。数值必须以实际统计为准；没有可靠统计时使用定性范围说明，不制造百分比。

## 5. 统一工作流与工作事项详情

### 5.1 工作流条目：统一展示，不新增权威业务数据库

建议建立只读/组合层 `WorkstreamItem`（名称是设计建议）：`kind`、`source_id`、`account_id`、`title`、`status`、`next_action`、`due_at`、`related_mail_ids`、`unread_count`、`provenance`、`suggested_actions`。它映射邮件、正式事项、等待和候选，**不成为它们的新主数据存储**。

默认视图按行动分组而不是按所有对象纯时间混排。用户可以切换全部/邮件/事项筛选，但不应需要理解多套重复的数据源。

### 5.2 事项详情信息层级

1. **顶部固定信息**：标题、进行状态、当前下一步、下一步责任人、明确日期和已确认来源。
2. **概览**：最新进展、最新变化、未解决问题；事实和 AI 推断分别标识。
3. **关联邮件**：尽量原位连续阅读，显示真实邮件关系及历史原文/附件入口。
4. **工作记录**：按事件时间展示人工确认、实际发送、日期变化、事实冲突和撤销操作；记录不能被摘要覆盖。
5. **就地操作**：回复、提醒、等待反馈、关联邮件、标记完成、调整下一步；高影响操作需要确认且可追溯。
6. **按需 AI**：当前事项上下文问答和可执行建议，随时可查阅来源。

### 5.3 三类日期必须独立

| 日期 | 来源 | 示例 | 处理原则 |
|---|---|---|---|
| 客户要求日期 | 客户邮件或正式要求 | “希望周四拿到” | AI 可提取候选，不视作我方承诺 |
| 我方承诺日期 | 用户或有权代表我方的明确沟通 | “我们周五交付” | 记录原始依据，改变时须明确确认 |
| 内部提醒日期 | 用户自己的跟进计划 | “周三检查进展” | 用户可自由设定，不自动修改对外承诺 |

### 5.4 状态拆分

- **通信状态**：未读、已读、已回复、已转发、发送待确认等，由邮件事实决定。
- **事项生命周期**：待开始、进行中、已完成、已取消，由正式业务事件决定。
- **下一步责任**：我方、对方、双方、待明确，是任务当前行动属性，不应覆盖生命周期。
- **AI 理解状态**：未分析、候选、不确定、已确认、已否定，是派生信息的生命周期。

“在等别人”是基于责任和提醒条件的工作视图，不是覆盖其他状态的唯一分类。

## 6. 邮件与工作事项的智能关联

### 6.1 分层判定机制

**第一级：确定性关系**。账号内的稳定邮件身份、真实回复引用（Message-ID / In-Reply-To / References）、用户此前确认的关联、受控的会话继承规则。注意：真实回复链只能证明通信关系，不自动证明单一工作目的。

**第二级：候选检索**。通过参与人、项目编号、已确认历史、时间上下文、主题等找出有限候选；其中主题相同或人员相同只是弱证据。

**第三级：AI 语义比较**。在许可范围内比较当前邮件与候选工作目标、历史变更和证据。输出候选及原因，不把模型的自报置信度直接当作校准概率。

### 6.2 交互原则

- 在当前邮件旁以单行轻提示：`可能关联：网络方案交付 · 关联 · 其他 · 忽略`；点击依据才能展开解释。
- 接受时写入**邮件-事项关系及事件**，不自动修改任务截止、完成状态或客户承诺。
- 拒绝、修改、解除关联都有记录，可撤销，优先于下一次模型推断。
- 用户可授权某个已确认的真实会话链自动延续关联；新主题相同邮件仍需重新评估。
- 一封邮件可对应多个事项；未关联的邮件保留原收件箱可见性。

### 6.3 纠错后的“学习”

优先通过持久化规则/否定记录实现：`mail/thread → rejected work link`、用户确认新关系、纠错依据和时间。不要把一次否定过度推广到所有相似邮件。没有实质新证据时抑制重复提议；出现新证据时可以重新提示，但必须说明理由。

### 6.4 关系数据建议

`WorkLink` 最少表达：`link_id`、`account_id`、`mail_id`/`thread_identity`、`work_item_id`、`origin=manual|inherited|ai_candidate`、`state=proposed|confirmed|rejected|removed`、`evidence_refs`、`rule_version`、`created_at`、`confirmed_at`、`revision`。实际落地前应对照现有任务关联表，尽量扩展而非另建重复表。

## 7. 工作记忆：事实优先于生成摘要

### 7.1 三层记忆

| 层 | 内容 | 保存策略 | 权威性 |
|---|---|---|---|
| 原始证据 | 邮件、附件、收发关系、时间 | 由邮件服务/受控缓存管理 | 原始沟通记录 |
| 正式工作事实 | 确认的承诺、决定、截止、工作状态、关联、纠错 | 正式任务/事实记录、版本历史、备份恢复 | 业务权威层 |
| AI 派生理解 | 摘要、候选关联、可能冲突、语义索引 | 可重建、可否定、存权限与模型版本 | 非权威辅助层 |

**业务约束**：不能把对方的“希望”写成我方已承诺；不能把最新邮件简单覆盖旧决定；不能因为模型未检索到旧事实就认定它不存在；无法解密正式事实时必须报告恢复状态、保留原文件并冻结受影响写入。

### 7.2 事实记录逻辑字段

`fact_id`、`account_id`、`project_id`、`work_item_id`、`fact_type`、`content`、`source_mail_ids`、`evidence_range`、`occurred_at`、`effective_at`、`recorded_at`、`status`、`confirmed_by`、`supersedes_id`、`version`、`model_version`（如由 AI 提取）。这是**逻辑契约**，不是批准创建新表。

### 7.3 记忆技术策略

当前优先复用 `memory/store.py`、`memory/merge.py`、`tasks/store.py`，强化恢复、权限、纠错、时间与证据。可在未来独立评估 Mem0/Hindsight 等开源语义记忆技术，但**V1.0 不包含集成 PoC，不要求新增向量数据库或图数据库**。后续若引入第三方引擎，应通过可替换 Provider 实现，且绝不取代正式业务事实主数据。

## 8. AI 主动性与注意力管理

### 8.1 四级呈现机制

| 级别 | 名称 | 适用情况 | 用户感受 |
|---|---|---|---|
| L0 | 静默理解 | 已授权的摘要、候选检索、普通历史关联 | 不打扰、不抢焦点 |
| L1 | 就地建议 | 当前阅读邮件时的潜在日期变化、候选任务/关联 | 在当前上下文中出现，可以忽略 |
| L2 | 工作台关注 | 重要但非即时变化、到期趋势、冲突待核对 | 打开首页集中看到，不弹窗 |
| L3 | 主动通知 | 用户明确设置的提醒、可靠的发送未知/失败等系统异常 | 可中断，受权限和免打扰规则约束 |

AI 自行推断的“紧急”不能单独触发 L3；没有经过校准的模型分数不能充当通知门槛。

### 8.2 Attention Decision Engine（逻辑层）

输入：事件来源、正式事项状态、截止/提醒时间、用户显式偏好、当前页面、是否重复、证据充分度、可用授权。流程：**权限检查 → 事件去重 → 与事项合并 → 识别变化 → 选择 L0–L3 → 记录建议状态 → 可撤销反馈**。

- 一件工作聚合多封邮件的重复催促；有实质变化（例如新期限）才重新提升关注。
- 普通 AI 建议默认有限展示、其余集中收纳；具体条数是待实测参数。
- “关闭提醒”“稍后”“永不提醒该类”“不是同一事项”“已完成”必须是**不同动作**。
- 设安静、平衡、积极三个偏好层级；默认建议平衡，但不让用户首次使用先做复杂配置。
- 确定性系统异常与用户明确设置的提醒不能被普通 AI 注意力预算悄然吞掉。
- 专注/免打扰时段可延后非紧急通知，不应阻断邮件本身同步与基本操作。

### 8.3 建议生命周期

`discovered → eligible → shown → accepted | dismissed | snoozed | rejected | superseded | expired`。需保留同源事件键、相关事项、证据版本、上次展示时间、用户反馈和去重指纹。若证据失效，撤销尚未采纳的建议；不得悄然反向修改已确认业务事实。

### 8.4 安全默认值

- L0 不等于擅自传数据到外部模型：即使是静默理解也必须事前具备组织允许及相应用户授权。
- 如果 AI 功能关闭，自动理解与出站队列不得继续发出新的模型请求；手动邮箱、人工待办和明确提醒仍正常工作。
- 对未分析邮件，不因没有 AI 关注事件而降低其原始收件箱可见性。

## 9. 上下文感知 AI 交互

### 9.1 一个助手，三种入口

1. **就地 AI**：阅读邮件附近显示摘要、回复草稿、提取待办等一键能力。
2. **上下文侧栏**：连续讨论复杂邮件、事项历史和决策差异；用户可固定当前对象。
3. **Ctrl+K / 全局命令**：快速搜索跨邮件信息，普通确定性命令由程序直接完成，无须每次调用模型。

共享同一工具、权限、上下文和记忆规则，不另建互相隔离的 AI 助手业务系统。

### 9.2 上下文绑定

建议的 `AIContext` 逻辑契约：`account_id`、`conversation_id`、`view_type`、`selected_object_ids`、`pinned_context`、`allowed_sources`、`permission_policy`、`context_version`、`snapshot_at`。

- 默认绑定当前选中的邮件/会话/事项；要扩大到历史邮件、其他项目或敏感范围，需要明确授权和可见范围。
- 用户切换页面时，新请求可以跟随新上下文；**已经提交的请求继续绑定其原始上下文快照**。
- 用户可将会话固定到某事项，切换邮件不偷偷改主题。
- 过期后台结果不得在切换账户/页面后写入新草稿、新事项或不相干的右侧详情。
- 每次 AI 输出至少说明：使用了哪些来源、检索/阅读边界、不确定内容；关键引用可返回原文。

### 9.3 AI 操作权限阶梯

| 类型 | 典型动作 | 权限与确认 |
|---|---|---|
| 查询 | 搜索、摘要、解释历史 | 经授权直接返回，有来源与范围 |
| 内容草稿 | 回复草稿、润色 | 可编辑、可撤销，不发送 |
| 工作变更建议 | 新建/关联/修改事项、确认截止 | 展示旧值/新值/依据，用户确认后正式写入 |
| 高影响外部操作 | 发送、删除、正式完成等 | 用户明确触发；模型不能绕过程序的权限检查 |

**关键体验**：AI 生成「回复客户周五可交付」后应就地进入现有邮件草稿编辑器；检查收件人、附件、日期变化后由用户发送。用户发出邮件后，仅更新已确认的通信事实，不自动关闭事项。

## 10. 数据权威性、权限与恢复

### 10.1 唯一权威来源矩阵

| 数据 | 权威来源 | 可重建的派生层 | 禁止行为 |
|---|---|---|---|
| 邮件原文、发送结果 | Coremail 服务器与可靠的发件提交日志；本机缓存为加速 | 摘要、检索索引 | 凭 AI 输出替换原始邮件、盲目重发未知发送 |
| 正式任务、用户确认的下一步/状态 | 现有正式任务库；Excel 迁移权威需另定 | 工作台组合视图 | 两边无声双向覆盖 |
| 确认的邮件-事项关联 | 正式关系与事件记录 | 候选关联、相似度索引 | 未确认候选直接修改工作状态 |
| 人工确认事实与纠错 | 受保护的事实/审计记录 | AI 提取摘要、向量索引 | 因模型重算或丢密钥静默清空 |
| AI 候选建议 | 派生记忆与建议生命周期 | 可过期/重建 | 当作正式承诺或已完成 |
| 提醒规则 | 用户显式设置 + 正式事项时间 | 建议排序 | 由 AI 静默建立不可见的永久屏蔽 |

### 10.2 安全与隐私约束

- 统一 AI 出站策略控制：组织批准的 endpoint、账号、敏感类别、共享邮箱/加密邮件的额外边界、授权撤销、模型调用日志脱敏。
- 共享邮箱与不同账号之间隔离检索/记忆；切换账号时丢弃旧会话过期结果。
- 邮件 HTML/附件属于不可信内容，不能通过提示词获得更高权限；工具实际权限由应用服务校验。
- 日志和测试报告不得落真实正文、密钥、Token、证书和敏感联系人信息。
- Windows DPAPI 保护本机用户密钥，但备份/换机恢复仍需明确支持策略。历史正式记录需要备份与恢复验证。
- 邮件发送出现 `Unknown` 时，界面提示「结果待确认」，提供核查已发送与人工确认路径，不直接称失败并鼓励重复发送。

### 10.3 只读应真只读

打开事项详情、搜索结果、工作记忆历史等，应避免无告知触发正式状态写入或企业邮件出站。若产品允许后台自动分析，需独立的用户设置、队列/权限策略和显式状态显示；不能把“正在阅读”悄悄转换成“发送邮件内容给 AI”。

## 11. 端到端用户旅程与异常路径

### 旅程 A：早晨进入工作台

1. 展示已确认工作、未检查邮件、在等反馈和精选建议；显示数据同步/分析边界。
2. 用户选择一项工作，右侧直接展示下一步及相关邮件。
3. 若 AI 关闭或尚未完成分析，展示普通邮件与人工任务，不显示“工作已清空”。
4. 离线时说明缓存范围，完整搜索/同步能力受限但已有数据可继续查看。

### 旅程 B：客户新要求与邮件回复

1. 新邮件进入完整收件箱，不因 AI 判断“忽略”而消失。
2. 用户阅读；AI 可展示候选摘要及日期/任务关联建议。
3. 用户点回复，AI 可生成可编辑草稿，默认当前邮件引用关系。
4. 发送经用户确认；如出现未知状态，保留待确认提示并禁止自动盲重试。
5. 如果回复承诺以后完成工作，事项仍未完成，允许轻量设跟进日期。

### 旅程 C：跨邮件事项跟进

1. 用户确认把某邮件关联到已有事项；不复制邮件。
2. 新的真实回复链邮件按获授权规则延续；跨会话由 AI 提建议。
3. 在事项详情一眼看到最新确认结论、下一步、关联邮件与历史时间线。
4. AI 发现客户变更请求时提示冲突，用户确认后才更改正式事项。

### 旅程 D：等待别人

1. 用户设置“等待客户回复至某日”。
2. 明确时间到时由普通程序按规则提醒；AI 可生成催办草稿但不发送。
3. 收到疑似回复时提示检查是否完整解决，不能凭同主题回复自动解除。
4. 用户明确确认解除等待；任务未必同时结束。

### 旅程 E：错关联与记忆纠错

1. AI 推荐错误事项，用户选择“关联到别的事项/不相关”。
2. 记录人工纠正事件，保持原邮件可查；去掉错误展示关联。
3. 后续相似邮件不重复按同样弱证据干扰用户，除非有新实质证据。
4. 发生事实冲突时旧事实仍留历史，AI 不能用新摘要覆盖原始承诺。

### 旅程 F：AI 无法使用

1. 模型超时/企业策略禁止/用户关闭：收读写找与手动任务完整可用。
2. AI 建议显示暂停或不可用，不捏造处理结论。
3. 队列停止新增不合规请求，历史正式记录仍可读。
4. 恢复后不得重复生成正式任务或重复执行用户已确认操作。

### 12.1 模块复用/改造/暂缓矩阵

| `ai/agent.py` / `ai/tools.py` | 工具调用、检索问答、操作规划 | 单一 AI 与当前上下文相绑定 | **增强权限、证据和上下文** |
| `memory/store.py` / `memory/merge.py` | 派生事实、项目历史、合并替代 | 来源、时间、人工纠正优先、恢复保护 | **P0/P1 逐步改造** |
| `tasks/store.py` | 正式任务、修订及关联 | 继续作正式事项权威，扩展关系/事件 | **复用，兼容迁移** |
| `outbox/service.py` | 持久化发送意图与 Unknown | 保留可靠发送恢复 | **保护现有资产** |
| `app/shell.py` / QWebChannel | UI 与后端桥接、线程执行器 | 生命周期与过期结果隔离 | **兼容性演进** |
| 现有甘特/周报/复杂依赖 | 已有高级能力 | 作为可选专业入口 | **保留、不继续扩张** |
| Mem0/Hindsight/向量图谱 | 未作为正式现有集成确认 | 将来必要时评估语义层 | **本期暂缓** |

### 12.2 逻辑服务边界（不要求一次性落地）

```text
UI / Unified Workstream / AI Sidebar
        |
    App Services  ← 权限校验 / 状态变更 / 事务 / 事件
        |-- Mail & Conversation Service → Coremail adapter / cache / outbox
        |-- Work Item & Follow-up Service → 正式 task store
        |-- Relation Service → 可审计的确认关联
        |-- Evidence & Memory Service → 确认事实 + AI 派生记忆
        |-- AI Orchestrator & Context Manager → 合规策略 / 查询 / 草稿 / 候选
        |-- Attention Engine → 候选去重、级别与通知策略
```

原则：UI 发出意图；应用服务拥有正式状态机、事务和权限；邮件协议层负责服务器通信；模型输出仅是候选理解和表达。保留现有 Bridge 兼容，避免一次性拆完当前聚合后端。

### 12.3 设计层接口示例（非实现签名）

- `list_workstream(filter, account, cursor)`：组合正式事项、邮件、提醒与候选，返回来源/覆盖信息。
- `get_work_item_detail(id)`：只读返回正式状态、下一步、关联证据和事件历史。
- `propose_mail_link(mail_id, candidate_scope)`：返回候选与理由，不写正式关系。
- `confirm_mail_link(mail_id, work_id, evidence)` / `remove_mail_link(link_id)`：正式事务、审计事件。
- `query_ai(context_snapshot, request)`：权限先行，结果绑定请求时的上下文版本。
- `set_followup(source_id, when, rule)`：显式提醒设置，避免另建不相干任务主记录。
- `record_suggestion_feedback(suggestion_id, action)`：采纳/拒绝/暂缓/纠错，不混淆已完成。

## 13. 交互细节与状态反馈规则

| 场景 | 必须反馈 | 禁止行为 |
|---|---|---|
| AI 未授权/关闭 | 清楚显示“未启用 AI；邮件可正常使用” | 宣称智能清单已覆盖全部工作 |
| AI 检索部分数据 | 来源数量、范围、失败/截断说明 | 用局部证据回答全局绝对结论 |
| 搜索无结果 | 区分本机缓存、服务器、存档；保留查询与返回路径 | 搜索标题已变但展示旧列表 |
| 新邮件关联候选 | 关联依据、确认/修改/忽略 | 用主题相似自动隐藏原邮件 |
| 发送不确定 | 显示“结果待确认”，提供人工核查 | 自动重发、宣称必然未发送 |
| 任务完成 | 用户动作或可靠正式事件、可撤销与留痕 | 因一封回复直接关闭事项 |
| 记忆不可解密 | 明示受影响数据、冻结受影响写入、提供恢复路径 | 悄悄清空并重新生成密钥覆盖用户纠错 |
| 低分辨率 | 标题可辨、上下文可读、核心动作可达 | 工具栏挤占全部标题和正文 |

键盘交互的统一目标：Tab 焦点有序，J/K（若保留）按屏幕可见顺序遍历邮件与事项，Ctrl+F 根据当前上下文进入正确搜索，Ctrl+K 打开全局命令，Escape 取消/返回时不意外丢失编辑内容。

## 14. 分阶段交付建议（非批准排期）

### 阶段 0｜可信底座与现存断点

优先：回复与完成状态解耦；今天/AI 空态与覆盖诚实；企业 AI 出站门禁及取消；正式记忆恢复保护；从今天子页搜索错误；发送未知状态回归保护。此阶段的重点是**确保现有能力不造成错误承诺或错误安心感**。

**阶段门**：无未经允许的模型出站/越权写入；未知发送不盲重试；关键正式记录不可静默丢失；已复现搜索断点修复且回归通过。

### 阶段 1｜核心邮件与工作体验收敛

统一工作流选择模型；详情阅读连续性；轻量跟进；事项详情三视图；合并重复展示；搜索来源提示；固定群组检索及工具栏适配。可同时进行不少于五个工作日的有限范围试用，优先修正实际反复发生的体验问题。

**阶段门**：核心八场景能够完整走通；未读/等待/任务都可找回原始依据；操作不会因换视图丢失上下文；鼠标与键盘一致；不增加重复主数据。

### 阶段 2｜证据驱动的 AI 工作辅助

把已有摘要、草稿、候选关联和记忆融入就地建议/侧栏/命令入口；补齐建议生命周期、人工纠错、证据和注意力分层；工作事项与历史事实时间线逐步增强。

**阶段门**：合成回归覆盖同主题不同事项、日期冲突、否定、转发旧决定、多事项邮件、误关联纠正、模型超时、切换账号；事实引用可打开；AI 不自动发送、不误改正式状态。

### 阶段 3｜有需求证据才扩大

只有当真实场景表明现有检索/记忆不足时，才决定是否评估 Mem0/Hindsight、本地向量索引、跨文档知识和更复杂任务视图；不得因技术流行而扩大范围。

### 与现有正式路线图的关系

本方案**不修改** `docs/roadmap/待实现功能.md`。如果产品负责人后续批准实施，请由 Work/Claude Code 逐项对照代码与既有排期，形成实施差异表，再只维护原正式任务队列，避免出现第二份相互冲突的“待实现”列表。

| AC-10 | AI 已许可但中途撤销授权 | 队列停止新增出站，AI 功能暂停，正式工作与原邮件保持可用 |
| AC-11 | 工作记忆密钥缺失/损坏 | 受影响数据明确报错且保留，不自动用空记忆覆盖历史 |
| AC-12 | 发送请求超时但结果未知 | 状态待确认，无自动重复发送；支持人工核查 |
| AC-13 | 1280×720、125%/150% 缩放，侧栏展开 | 页面标题、邮件正文、关键回复动作仍可达、可辨 |
| AC-14 | 仅键盘从工作台跨邮件/事项/等待遍历 | 焦点和选中模型一致，无隐藏项跳跃与意外动作 |

验收应分清：纯合成数据、授权测试账户、真实个人试用三种证据等级。不要让静态代码检查替代运行验证。工作时间、差错和采纳率先记录基线，后设改进目标。
