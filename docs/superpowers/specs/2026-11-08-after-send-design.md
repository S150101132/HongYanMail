# F1 发后跟进收进后端（设计，2026-11-08）

来源：第二轮 `/improve-codebase-architecture` 评审的候选 1，用户逐题拷问后确认（Q1–Q12 全部按推荐）。

## 现状和问题

一封回复 / 转发发出后有三件事：理解层卡片标「已回复 / 已转发」（R3a）、提议关闭关联任务、助理起草的邮件提议记一条进展。现在由页面判断，`tasks.js:598`、`understand.js:184`、`ai.js:869` 三处层层覆盖全局 `sendOutcome`，各自再调后端。

- 写信弹出窗口发出时，主窗口收到的发送结果 `meta` 为空，不标卡片、不提示；关闭任务的提示还要求在主窗口（`READER_MID`）。撤销倒计时中关掉弹出窗口同样丢 `meta`（`compose.js:69`）。
- 时机不一致：后端只在 Accepted 时写缓存 `replied`；页面在 Queued 时就标卡片、提示。
- 转发来源 `sourceMid` 只在页面的 `C.draft` 里，后端草稿不知道；助理计划和写信窗口的对应只在页面 `S.assistDrafts` 里。

（评审报告里「离线补发的回复不提示关闭任务」不成立：Queued 时已经提示过。）

## 决定

1. **后端决定发后的事**（Q1）。`_dispatch` 在 Accepted 时调用新 module，结果随发送结果返回；页面只显示。三处覆盖删掉，`meta.source` / `meta.how` 不再需要。
2. **草稿记住来源**（Q2）。转发也把来源邮件存进草稿记录（回复已有 `reply_source_id`），撤销期满、离线补发、弹出窗口都拿得到。
3. **只在 Accepted 时触发**（Q3）。进离线发件箱（Queued）时不标、不提示，补发成功后再做；与缓存 `replied` 同时。每封只做一次。
4. **提示在主窗口显示**（Q4）。弹出窗口发出或已关闭都一样。
5. **范围**（Q5）。只管这三件事；「邮件已发送」「已放入发件箱」等普通提示仍在 `sendOutcome`。
6. **结果字段**（Q6）。Accepted 的结果（`sendResult`，以及 `outboxFlushed` 里的每一项）带 `after`：`how`（`reply` / `forward`，新邮件为空）、`answered`（`{mid, how}` 或空）、`tasks`（可关闭的任务，最多 3 个，id + 内容）、`plan`（助理进度提议或空）。文案和按钮不变：「已处理」「关闭任务」「查看」。
7. **助理草稿**（Q7）。`assistant_draft_compose` 把计划 id 存进草稿记录，`_dispatch` 自己认出，去掉 `S.assistDrafts`。
8. **位置**（Q8）。新 module `coremail_desktop/app/aftersend.py`，不依赖 Qt，对外一个调用：「这份草稿已被服务器收下，返回 `after`」。理解层卡片、任务中心、助理计划、缓存由 `MailBackend` 传入。
9. **不加「已转发」缓存标记**（Q9），列表不变。
10. **不加术语**（Q10）：用现有的「已回复 / 已转发」「关联任务」。
11. **不替用户开任务中心**（开发时补）：没用过「任务」的账号（还没有 `tasks` 目录），发信不会建任务库，`tasks` 为空。

## 测试（Q11，TDD）

从 `MailBackend` + 演示服务器走：直接发送；撤销期满（`release_send`）；离线补发（Queued 时 `after` 为空，补发后带上）；转发标已转发；理解层关闭时不标卡片；助理草稿发出带 `plan`、只一次。原来查三处覆盖的源码字符串测试改为查「覆盖已删、`after` 有人处理」。
