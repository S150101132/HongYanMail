# 任务中心 + Excel 无损迁移（v0.9）— 设计文档

日期：2026-10-20　状态：已实现，待真机验收（[记录](../../releases/2026-10-20-task-center.md)）。用户确认（2026-10-20）：第 10 节全部按建议执行；做完即可切换，数据放在哪里由实现决定（见第 3 节：`HongyanData/tasks/`）。
范围：v0.9 只做任务中心和迁移，**不含 AI**；v1.0 再做 AI 关联邮件、自然语言更新任务。

## 1. 背景与目标

用户现在用 ChatGPT Work 维护 Saudi-NG 的两份工作簿（`未完成任务.xlsx`、`已完成任务.xlsx`），规则写在任务目录的 `AGENTS.md`、`任务管理说明.md` 和上级 `AGENTS.md` 里，每批修改后手写 `变更记录.md` 并本地 `git commit`。用户已决定：

- 彻底告别 Excel 手改和 ChatGPT Work，任务只在鸿雁里改；
- 只在这台电脑上用，不需要手机端；
- 顺序：v0.8 问邮箱（已完成）→ v0.9 任务中心 → v1.0 AI。

目标：

1. 鸿雁成为任务的**唯一写入方**，数据加密保存在本机，和邮件缓存分开。
2. 两份工作簿**无损**导入，导出后逐格比对一致；每次修改后自动导出 Excel + JSON 到任务目录，用户自己 `git commit`。
3. 现有规则（状态枚举、完成日期默认沙特当天、负责人默认本人、不补造信息、改完列出全部未完成任务……）变成代码里的校验，而不是靠助手自觉。
4. 不用 AI、不登录邮箱也能完整使用。

不做的事：

- 不做 Project / Person / Decision / AIProposal 等独立对象（讨论稿第 6.2 节），v0.9 只有三张表。
- 不运行 `git`，不改 `AGENTS.md` 等说明文件（切换时由用户自己改）。
- 不导入 `任务边界与验收说明.md`、`历史备份/`、`.task316-work/`。
- 不做提醒、通知、对外发信。

只读了两份工作簿的 XML 结构和单元格类型，以及说明文档和 `git log`。下表只有结构、数量和格式；没有抄录任务正文。

| Git | 40 个提交（2026-10-07 起）；基线标签 `git-migration-baseline-2026-10-07`；`*.xlsx` 设为 binary |

鸿雁代码中可以直接复用的部分：

- `app/cache.py` 和 `archive/catalog.py`：SQLite 里只存 AES-GCM 密文（`nonce + 密文`，AAD 绑定行 ID）；256 位密钥用当前 Windows 用户的 DPAPI 包装后，存在旁边的 `.key` 文件里。
- `app/shell.py` 的 `Bridge.run`：每类方法有自己的单线程池（`hongyan-mail`、`hongyan-ai`、`hongyan-archive`……）；只有固定错误码能传到页面。
- 数据目录：程序旁边的 `HongyanData/`（这台电脑写不了用户配置目录）。
- `.venv` 里没有 `openpyxl`，也没有 `tzdata`（所以 Windows 上 `zoneinfo.ZoneInfo('Asia/Riyadh')` 不能用）。

## 3. 关键决策

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| Excel 读写 | **只用标准库** `zipfile` + `xml.etree`，不引入 openpyxl | 读取只需要单元格的值和类型（约 150 行）。导出时用导入时保存的格式模板重新生成固定版式，输出由我们完全控制：保留空格和换行、同样的数据生成**完全相同的字节**（git 不会出现无意义的改动）。openpyxl 读入再保存会把整个文件重新序列化，还要额外验证打包。代价是 Excel 的兼容细节要自己处理，用往返校验和阶段 A 的人工打开检查来兜底 |
| 写入源 | 切换后 SQLite 是唯一真相；Excel / JSON 只是导出 | 对应讨论稿第 7.4 节「单一写入源」|
| 存储 | `HongyanData/tasks/tasks.db` + `tasks.key`，与 `cache/` 分开，不按邮箱账号区分 | 缓存可以随时清空重建，任务是正式记录；不登录也能用任务 |
| 加密 | 照搬 `cache.py`：每行一个 AES-GCM blob，AAD 写 `task:<编号>` 等 | 已验证过的写法；防止行被替换或调换 |
| 沙特时区 | 固定使用 `timezone(timedelta(hours=3), 'Asia/Riyadh')` | 沙特没有夏令时，+03 是固定的；不需要为此引入 tzdata |
| 审核 | 不建 AIProposal 表；`TaskEvent` 和 `TaskMailLink` 各加一个 `review` 字段（已确认 / **待审核** / 已驳回）| v0.9 用它来处理「外部改动的 Excel」，v1.0 的 AI 建议也写成待审核事件，用同一套界面 |
| Git | 鸿雁不执行 git，只导出文件，并给出建议的提交说明 | 用户的明确要求；也避免误提交 |

## 4. 数据模型

### 4.1 表结构

```sql
CREATE TABLE tasks(id INTEGER PRIMARY KEY, rev INTEGER NOT NULL, blob BLOB NOT NULL);         -- AAD 'task:<id>'
CREATE TABLE events(seq INTEGER PRIMARY KEY AUTOINCREMENT, task_id INTEGER NOT NULL, at REAL NOT NULL,
                    review TEXT NOT NULL DEFAULT 'confirmed', blob BLOB NOT NULL);               -- AAD 'event:<task_id>:<at>'
CREATE TABLE mail_links(id INTEGER PRIMARY KEY AUTOINCREMENT, task_id INTEGER NOT NULL,
                        review TEXT NOT NULL DEFAULT 'confirmed', blob BLOB NOT NULL);           -- AAD 'link:<task_id>'
CREATE TABLE kv(k TEXT PRIMARY KEY, blob BLOB);   -- 导出模板、导出状态（文件指纹）、设置、导入报告、阶段
CREATE INDEX events_task ON events(task_id, at);
```

明文列只有编号、版本号、时间戳和审核状态，正文全部在密文里。336 条任务启动时全部解密到内存，查找在内存里完成（和 cache.py 一样）。

### 4.2 Task（blob 内的 JSON）与 15 列的对应

| 列 | 字段 | 类型 / 约束 |
| --- | --- | --- |
| A 编号 | `id` | 正整数，就是主键；不能修改，跨文件唯一，不复用 |
| B 系统 | `system` | 文本（BI 照原样保留，不改成 NG BI）|
| C 任务内容 | `content` | 文本，必填 |
| D 优先级 | `priority` | `高`/`中`/`低`/空 |
| E 状态 | `status` | 7 个状态之一（见 5.1）|
| F 最新进展 | `latest` | 文本 |
| G 负责人／责任边界 | `owner` | 文本 |
| H 开始日期 | `start` | 日期 |
| I 计划完成日期 | `due` | 日期 |
| J 结束日期 | `end` | 日期（完成和取消都用这一列）|
| K 阻塞与依赖 | `blockers` | 文本 |
| L 下一步 | `next` | 文本 |
| M 最近更新日期 | `updated` | 日期 |
| N 进展与历史记录 | `history` | 文本，只能追加 |
| O 完成／验收标准 | `acceptance` | 文本 |

**日期字段**统一存成 `'YYYY-MM-DD'`、`''`（空），或者 `{'text': '原文'}`（导入时遇到不能解析的文本，原样保留并在报告里列出；之后编辑时必须改成真正的日期）。
**内部字段**（不导出到 Excel）：`order`（在原工作表里的行序，导出时保持原来的顺序；新任务和新归档的任务排在末尾）、`cells`（只记录特殊单元格的原始类型，比如「历史列是数字」，这样没改过的格子导出后类型不变）、`created`。

所在工作表**不单独存储**，由状态推出来：已完成 → 已完成任务；已取消 → 已取消任务；其他 → 未完成任务。这样就不可能出现「状态和所在表不一致」。

### 4.3 TaskEvent（时间线，只增不改）

```json
{"kind": "progress", "date": "2026-10-20", "actor": "user", "batch": "b-…",
 "changes": {"latest": ["旧值", "新值"], "history": ["", "追加的一行"]}, "note": "依据 / 理由"}
```

- `kind`：`imported`（导入）、`created`、`edited`、`progress`、`completed`、`canceled`、`reopened`、`external`（从外部改动的 Excel 读进来的）、`restored`。
- `date` 是业务日期（沙特日期，默认当天，可以手填）；`at` 是实际写入时间（UTC）。
- 同一次操作（比如同时归档两条）用同一个 `batch`，导出和建议提交说明都按 batch 处理。
- `review`：v0.9 由用户操作产生的都是「已确认」；`external` 事件是「待审核」，接受后才写入 Task。v1.0 的 AI 建议也走这条路。
- 每次修改在**同一个 SQLite 事务**里做三件事：更新 `tasks`（`rev+1`，同时检查前端带来的 `rev`，不一致报 `TASK_CONFLICT`）、写事件、写 kv 里的「待导出」标记。

### 4.4 TaskMailLink

```json
{"mid": "…", "messageId": "…", "subject": "（快照）", "date": "2026-10-14 10:02", "source": "server|archive|eml",
 "actor": "user", "note": ""}
```

打开链接时先按 `mid` 找；找不到再按 Message-ID 在缓存和本地存档里找（邮件被移动后 `mid` 可能变）；都找不到就显示「邮件不在本机」，不去猜。v0.9 是否提供手动「关联到任务」见问题 Q5；表在 v0.9 就建好，v1.0 直接用。

## 5. 规则如何变成代码

规则写成 `coremail_desktop/tasks/rules.py` 里的纯函数，后端每次写入前调用，单元测试逐条覆盖。来源：上级 `AGENTS.md` 的任务管理章节、任务目录 `AGENTS.md`、`任务管理说明.md`。

### 5.1 校验（不满足就拒绝保存，返回固定错误码）

| # | 规则 | 实现 |
| --- | --- | --- |
| R1 | 状态只能是 未开始、待处理、进行中、受阻、待验收、已完成、已取消 | 枚举；其他值 → `TASK_STATUS_INVALID` |
| R2 | 编号唯一、永久，新编号 = 全部任务（包括已归档）的最大编号 + 1，不复用 | 只由后端分配；修改请求里带 `id` 变化 → `TASK_INVALID` |
| R3 | 改成已完成或已取消只能通过「标记完成」「取消任务」操作；普通编辑不能直接改成终态 | 编辑接口拒绝终态 |
| R4 | 完成时没给日期，结束日期 = **报告当天的沙特日期**；给了日期就用给的 | `riyadh_today()`；对话框里预填当天，可以改 |
| R5 | 取消必须写原因；保留原来的结束日期，不把取消日期写成完成日期 | 原因必填，写到事件和历史列；取消日期见 Q3 |
| R6 | 改成「受阻」时必须填写阻塞与依赖 | 只在切换到受阻时检查，导入的旧数据不检查 |
| R7 | 优先级只能是 高/中/低/空；日期必须是真实日期 | 不允许新写入文本日期 |
| R8 | 「进展与历史记录」只能追加 | 记录进展会在末尾加一行 `YYYY-MM-DD：内容`，前面的原文逐字不变。确实要改旧文字时用「更正历史」，必须写理由，旧全文保存在事件里 |
| R9 | 重新打开：回到未完成，编号和历史不变 | 状态由用户选（默认进行中），结束日期清空，旧值记在事件里 |

### 5.2 默认值（只有下面这些会自动填写，其他一概不补）

| 场景 | 自动填写 | 不会填写 |
| --- | --- | --- |
| 新建任务 | 编号；状态「未开始」（用户可以改成进行中）；负责人默认本人（具体写法见 Q4）| 优先级、开始日期、计划完成日期、验收标准、依赖 |
| 记录进展 / 修改业务字段 | 最近更新日期 = 事件日期（默认沙特当天）| 状态不会因为进展自动变化；「下一步」不会自动变成「已执行」|
| 完成 | 结束日期（R4）、最近更新日期 | 验收结果 |
| 导入、导出、格式或结构调整 | 什么都不改 | **不更新最近更新日期**，也不产生业务进展 |

「逾期」只在计划完成日期是真实日期、任务没有结束、并且早于沙特今天时才显示。没有计划日期的任务永远不算逾期。

空着的验收标准、负责人边界，在详情页标成「待确认」作为提醒，但**不阻止保存**；这对应「迁移时不集中追问，更新到这条任务时再问」的约定。

### 5.3 保存后的核验（对应「改完列出全部未完成任务」）

每次保存后，后端用一个新的数据库连接从磁盘重新读取并解密全部任务，检查：

- 编号唯一，最大编号没有减少，总数 = 上次总数 + 新建数；
- 已完成/已取消表里只有终态，未完成表里没有终态；
- 本次修改的字段和请求一致，其他字段没有变化。

然后返回**核验结果**：全部非终态任务（编号、系统、任务内容、状态；包括待处理、待验收），以及未完成/已完成/已取消/总数。页面固定显示这一块；没有未完成任务时显示「当前无未完成任务」。核验不通过时报 `TASK_VERIFY_FAILED`，这次修改回滚，并写入错误日志（日志里不记录正文）。

## 6. 导入、导出与往返校验

代码放在 `coremail_desktop/tasks/xlsx.py`（读写）和 `transfer.py`（映射、报告、比对、JSON）。

### 6.1 读取

- 支持的单元格类型：`s`（共享字符串，含富文本拼接）、`str`、`inlineStr`、`n`、`d`、`b`、`e`；`xml:space` 保留空格；读取 `date1904` 标记。
- 日期列：整数序列号 → 日期；`t="d"` → 取前 10 位；带样式但没有值的格子 → 空；其他文本 → `{'text': …}`，并记为异常。
- 文本列：值原样保存，不 `strip`，不转换换行；如果是数字单元格，保存它显示的文字，并在 `cells` 里记下原始类型。
- 版式检查：工作表名、第 4 行的 15 个表头必须完全一致，否则报 `TASK_IMPORT_LAYOUT`，不猜列的对应关系。
- 数据行：第 5 行起有内容的行；「只有编号」的占位行不导入，列在报告里。
- 安全上限：解压后总大小 ≤ 50 MB，行数 ≤ 10000，不跟随外部链接。
- 导入时同时保存**格式模板**（加密后放在 kv 里）：`styles.xml`、主题、列宽、冻结窗格、条件格式规则、数据验证列表、表格名称和样式、第 1–2 行的文字。这里面没有任务数据。

### 6.2 导入报告（只含数字和编号，导入前先显示给用户）

每张表的条数、编号范围、编号是否唯一、状态是否和所在表一致、各列空值数量、`t="d"` 格数、文本日期格数、数字型文本格数、前后有空格的格数、开始晚于计划/结束的条数、缺结束日期的已完成和已取消条数。**阻止导入**的情况：编号重复、终态出现在未完成表、非终态出现在归档表、表头不符。其他情况只提示，原值照样保留（对应「历史缺项保留，不推算补齐」）。

### 6.3 导出

每次导出三个文件，写到任务目录（切换前写到 `HongyanData/tasks/export-trial/`）：

| 文件 | 内容 |
| --- | --- |
| `未完成任务.xlsx` | 和现在同名、同版式，git 历史直接接上 |
| `已完成任务.xlsx` | 「已完成任务」「已取消任务」两张表 |
| `任务数据.json` | 全部任务（15 列用中文列名作键，外加内部字段）、全部事件、邮件链接；按编号排序，UTF-8，LF，缩进 1。文本格式，可以 diff，这就是新的「变更记录」|

生成方式：

- 用模板重写 `sheetData`；把表格范围、条件格式和数据验证的范围改成 `5..末行`；按文字长度估算行高（规则「根据文本长度调整行高」）。
- 文字一律写成 `inlineStr` 并加 `xml:space="preserve"`；日期写成序列号加 `yyyy-mm-dd` 格式；空格子保留样式，不写值。
- 未完成表一条都没有时，表格对象保留一行空数据行（Excel 的表格至少要有一行），读回来时这行算 0 条。
- ZIP 里的文件顺序和时间戳固定 → 数据一样时字节完全一样。
- 原子写入：先写到同目录的临时文件 → 读回来做往返比对 → `os.replace`。两份工作簿要么都替换，要么都不替换（先全部写好、校验通过，再依次替换；第二个替换失败就把第一个换回原文件）。

### 6.4 防止覆盖别人的修改

kv 里记录上次写出的每个文件的 SHA-256。下次导出前先算一下现有文件：

- 如果有 Excel 锁文件 `~$*.xlsx`，或者替换时报 `PermissionError` → `TASK_EXPORT_LOCKED`：数据库已经保存成功，只把导出标为「待导出」，关掉 Excel 后自动或手动重试。
- 指纹和上次写出的不一样（有人在 Excel 里改过）→ `TASK_EXTERNAL_CHANGE`：**暂停导出，不覆盖**。界面提供两个选择：「读入外部修改」（逐格对比，差异写成待审核事件，逐条接受或驳回）；「以鸿雁为准」（先把外部文件复制到 `HongyanData/tasks/displaced/`，再覆盖）。

### 6.5 往返校验

**定义**：两份工作簿 A、B 等价 =
三张表的任务集合相同、行序相同；每条任务 15 列规范化后的值相同（文字逐字相同，包括空格和换行；日期按日期比较；空和空相同）；工作表名、第 1–2 行、表头、表格名称、数据验证列表、冻结窗格、列宽都相同。

**允许且会在报告中列出的规范化**（打开 Excel 看不出区别）：`t="d"` 改成序列号；`str` 改成 `inlineStr`；行高重新估算。

**执行时机**：
1. 导入时：原文件 → 数据库 → 导出到临时目录 → 读回来 → 和原文件比较。不一致就拒绝导入，并列出不一致的「编号 + 列名」（不显示内容）。
2. 每次导出时：数据库 → 文件 → 读回来 → 和数据库比较，不一致就不替换文件。
3. JSON 同样读回来比较。JSON 还可以**完整恢复**（包括时间线），因为数据库被 DPAPI 绑定在这台电脑的这个用户上，换电脑或重装系统时就用 JSON 恢复。

## 7. 「变更记录.md」与 Git 的替代方案

| 现在（ChatGPT Work）| 以后（鸿雁）|
| --- | --- |
| 改之前 `git status`，记下修改前的提交编号 | 不需要：数据库事务加时间线就是修改前后的记录；导出前用文件指纹检查外部改动（6.4）|
| 两份表成对改、成对核验 | 由导出保证（6.3 的原子写入和往返校验）|
| 手写 `变更记录.md` | 时间线事件（依据、日期、改了哪些字段、旧值→新值）保存在数据库，并随 `任务数据.json` 导出，git diff 能看到每条改动 |
| 改完列出全部未完成任务 | 5.3 的核验结果，每次保存后自动显示 |
| `git add` + `git commit` | **由用户自己执行**。鸿雁导出后显示「已导出 3 个文件」和一条建议的提交说明（按这次 batch 生成，比如「更新302进展并核验任务清单」），可以一键复制 |

建议在切换当天由用户在 `变更记录.md` 末尾手写一条「自 2026-10-xx 起由鸿雁维护，后续变更见 任务数据.json」，之后不再改它（见 Q1）。`AGENTS.md`、`任务管理说明.md` 也由用户改为：工作簿由鸿雁导出，不要直接编辑。

备份：数据库每天第一次启动时、每次导入前、切换前，都用 SQLite backup API 复制到 `HongyanData/tasks/backup/`（保留 14 份，导入前的备份长期保留）。这些备份也是加密的，只能在这台电脑上用；能带走的备份是任务目录 git 里的 Excel + JSON。

## 11. MVP 验收

### 11.1 自动化测试（unittest；用测试里合成的工作簿，**不在仓库里放真实任务数据**；临时文件放在仓库里，测试结束后删除）

1. **读取**：各种单元格类型（s/富文本/str/inlineStr/n/d/b/带样式的空格）、date1904、前后空格和换行都原样保留。
2. **往返**：三张表，1500 字带换行的文字、前后空格、历史列是数字、`t="d"` 日期、空日期、文本日期 → 导出 → 读回来等价；同样的数据导出两次字节完全相同。
3. **版式错误**：表头不对 → `TASK_IMPORT_LAYOUT`；跨文件编号重复 → `TASK_IMPORT_DUPLICATE`；终态出现在未完成表 → 阻止导入。
4. **编号**：最大编号在已归档任务里时，新编号仍然是最大值 + 1；修改编号被拒绝；归档、重新打开、多次导入后编号不变。
5. **完成日期**：把时钟固定在 UTC 2026-10-20 22:30（沙特已经是 10-21），完成后结束日期是 2026-10-21；给定日期时用给定的日期。
6. **取消**：没写原因就拒绝；没给日期时不填结束日期（按 Q3 的结论）。
7. **受阻**：切换到受阻时阻塞与依赖为空就拒绝；导入的旧受阻任务不受影响。
8. **追加历史**：记录进展后，原来的历史原文逐字是新历史的开头；最新进展被替换，旧值在事件里；最近更新日期 = 事件日期。
9. **不补造**：只填任务内容就新建，优先级、开始和计划日期为空；没有计划日期的任务不算逾期。
10. **导入导出不改业务日期**：导入后再导出，最近更新日期不变，也没有业务事件。
11. **事务**：在写任务和写事件之间注入错误，两者都回滚；`rev` 过期返回 `TASK_CONFLICT`。
12. **核验**：保存后返回的列表包含所有非终态（包括待处理、待验收），四个数字正确；没有未完成任务时数量是 0，并显示固定文字。
13. **导出被锁**：有 `~$` 锁文件时报 `TASK_EXPORT_LOCKED`，数据库已经保存，标为待导出；解锁后重试成功。
14. **外部改动**：导出后改动文件 → `TASK_EXTERNAL_CHANGE`，文件没有被覆盖；读入外部修改后产生待审核事件，接受后写入任务，驳回后任务不变。
15. **空的未完成表**：能导出，重新导入是 0 条，表格对象有效。
16. **加密**：数据库文件里找不到测试用的明文标记；调换两行的 blob 后解密失败（AAD）；密钥解不开时报 `TASK_STORE_LOCKED`，程序不崩溃。
17. **JSON 恢复**：导出 JSON → 新建一个库 → 恢复 → 任务和时间线完全相同。

### 11.2 真实数据验收（用户在这台电脑上操作；记录里只写数量和是否通过）

1. 阶段 A：导入报告是 7/291/38，共 336，没有重复；异常列表和第 2 节一致（24 格 ISO 日期、1 格数字型历史、30 格前后空格、缺结束日期 1+31、日期顺序异常 1）；往返校验通过。
2. 用 Excel 打开导出的两份文件：三张表、下拉、着色、冻结、表格筛选、行高都正常。
3. MVP 场景（讨论稿第 12 节）：打开 #302 → 看原始历史和时间线 → 记录一条进展 → 「检查变更」看到差异 → 保存 → 核验面板列出全部未完成任务和总数 → 任务目录里的三个文件已更新 → `git diff 任务数据.json` 能看到这次改动 → 重新导入导出的 Excel，历史一条都没少。
4. 完成一条任务、取消一条任务、重新打开一条任务，三次核验和导出都正确。
5. 不登录邮箱、断网时，任务中心照常可用。
