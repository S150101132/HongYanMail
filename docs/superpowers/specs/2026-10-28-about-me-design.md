# 「关于我」：鸿雁对用户的长期记忆（Me1、Me2）— 设计文档

日期：2026-10-28　状态：Me1 已验收（[记录](../../releases/2026-10-28-about-me-me1.md)）；Me2 已实现，待真机验收（[记录](../../releases/2026-10-28-about-me-me2.md)）
依据：用户 2026-10-28 提出「从 AI 邮箱进化为个人 AI 工作助手」，参考 Meta Muse 的长期记忆；讨论后收窄为：**AI 了解我（岗位、项目、系统、人、工作方式），所有 AI 功能都带上；AI 先给初版，我改；之后从邮件持续更新。主动协作（提醒、自动处理）这次不做。**

## 1. 要解决的问题

| 现状 | 后果 |
| --- | --- |
| 问 AI（`ai/agent.py`）的系统提示词只有「你是用户工作邮箱的检索助手」，没有用户是谁 | 「我负责的系统」「我的上级」「我们项目」都无从理解 |
| 理解层（`ai/understand.py`）只知道姓名、主送 / 抄送、项目名单（负责 / 关注）、未完成任务、项目事实 | 判断「是不是要我做」只看邮件字面，不知道这件事是否归你管、发件人是谁 |
| 关于用户的信息散在几处：设置里的项目名单、理解规则、人物卡片「负责什么」（从项目事实里猜） | 没有一处能看到「鸿雁认为我是谁」，也没法纠正 |

## 2. 取舍（先列撤掉什么）

- **撤掉**：设置里单独的「工作记忆 · 项目名单」一节——并入「关于我」的「项目和系统」一组（数据和行为不变：负责 / 关注、系统归属、别名、任务中心的系统自动列入）。
- **撤掉**：人物卡片「负责什么」只从项目事实里猜——先看「关于我 · 人」里这个人的那条，再补项目事实。
- **不加**：新的 AI 入口、新的左栏页面、主动提醒、自动执行。
- **不变**：工作记忆的项目事实（M2）。分工：**关于我 = 变化慢、关于你自己**；**项目事实 = 变化快、关于项目里发生的事**。理解规则（发件人 / 关键词 → 分类）也保留，它精确、不花 token。
- **AI 不能自己改你的资料**：AI 记的新条目先「待确认」；你写过或改过的条目 AI 永远不能覆盖，最多提议。

## 3. 内容

一张短条目列表，分四组，每条一两句话（≤ 120 字）：

| 组 | 例子 | 来源 |
| --- | --- | --- |
| 我的岗位 | 「浪潮集团，沙特利雅得 NG 项目现场，复合角色（方案、产品设计、部署集成、报表开发、交付协调）」「具体岗位 / 职级未确认」 | 通讯录（部门、职务）、参考资料、已发邮件、任务 |
| 项目和系统 | 原项目名单：项目（负责 / 关注）、其下的系统、别名；**每个系统可带一句「我做什么 / 不归我」**，例如「NG BI（DataEase V1）：报表需求、SQL/KPI 口径、开发与核对通常要我执行或协调；不代表所有源系统故障由我修」 | 原项目名单 + 任务中心的「系统」+ 参考资料 |
| 人 | 「沙特分公司领导 · 直接领导（姓名待确认）」「TNOC · BI 需求和报表问题的来源之一」，可带邮箱；可以是一个人，也可以是一个部门 / 角色 | 已发邮件里常写给的人 + 通讯录部门 / 职务 + 参考资料 |
| 工作方式 | 「客户邮件用英文、同事用中文」「DBA、网络安全、AD 的专业操作不默认派给我，我负责协调跟进」 | 参考资料、已发邮件 |

**每组带一句用法说明和自己的字数上限**（借 Letta 记忆块的 `description` / `limit`）：拼进提示词时每组前写它怎么用，例如「项目和系统：『不归我』的部分不要写成要用户做」；单组超限只截那一组，不挤掉别的组。上限：岗位 600 字、项目和系统 1800 字、人 1400 字（2026-10-28 真机：带邮箱的人名条目 15 条约 1040 字，原 1000 截掉了最后一条），工作方式 600 字。

**边界和「没确认」同样要记**：参考资料里大量是「高关联，但不等于我负责修复」「领导姓名未确认」。它们直接决定判断结果（例如 MAXIMO 宕机 → 我协助定位、联系负责人，不是我去修），所以写成普通条目，不另设字段；AI 不得把「未确认」自行补成具体人名或职级。

每条记：`id、group、text、email（人那组可选）、by（user / ai）、src（来源：邮件 id、「参考资料」、「纠正」或空）、state（current / pending / past）、at`。
**被取代的不删，留作「以前」**（借 Graphiti「旧事实作废而不删除」和 Inbox Zero 的 `RuleHistory`）：确认了一条 `replaces` 的新条目后，旧条目变 `past`、记下被取代的日期，在组末「以前的 N 条」里折叠显示，可「恢复」。用户自己点删除才真删。和项目事实的历史做法一致。
上限：current 80 条、pending 20 条（超出时最旧的 pending 丢弃）；带进提示词的全文不超过 4000 字（超出时按组截断，并在资料页提示「太长，AI 只看到前 N 条」）。
存储：工作记忆库（`memory/store.py`，AES-GCM + DPAPI）的 kv `profile`；不另建库。关掉「理解新邮件」也照样可用（问 AI 要用）。

## 4. 初版：AI 起草，你改（Me1）

在「关于我」点「生成初版」（之后也可以「重新生成」——只产生待确认条目，不动已有的）。

取材（只读）：
0. **参考资料（可选，推荐）**：「生成初版」旁可「选择参考资料…」导入一个 .md / .txt（≤ 2 万字），例如用户从 ChatGPT 导出的个人工作记忆。它是用户自己给的，可信度高于邮件，但**可能过时、可以改**：AI 把它拆成条目，和邮件里看到的情况对不上时两条都列出并标「待你确认」。原文不保存（只保存拆出的条目），也不进仓库。历史经历（以前的国家、项目、学历）只留一条概括，不逐条进资料——它们不代表现在还要处理这些事。
1. 通讯录里自己的部门、职务（`oab:get`，已接好）。
2. 最近 3 个月已发邮件：统计主送最多的 20 个人，同事再查一次通讯录的部门 / 职务；外部只看域名。
3. 其中最新的最多 60 封的正文新写部分（每封 ≤ 600 字，去签名和引用，复用 W6 的 `style_sample` 思路）。加密邮件按「允许 AI 读取加密邮件」设置，未允许就跳过并在结果里写跳过几封。
4. 任务中心：我负责的未完成任务的内容和系统。
5. 现有项目名单、理解规则。

一次 AI 调用（约 3–4 万 token，带参考资料时），输出 JSON 条目；邮件内容照常当不可信数据，用随机标记包起来。
结果显示为**草稿**：每条可改、删、取消勾选，可手动加；点「保存」后生效（你改过的标 by=user）。没配 AI 时只用通讯录和项目名单生成岗位、项目两组，其他留空给你写。

## 5. 持续更新（Me2）

- **理解新邮件时顺带**：理解层的提示词带上「关于我」，输出多一个可选字段 `me`（最多 2 条，`{group, text, replaces}`），只在邮件**明确**说到你的新情况时写：被指定为某事的负责人 / 接口人、岗位或上级变化、新的对接人、不再负责某事。不增加 AI 调用。外部邮件只能提议「人」和「项目和系统」两组。
- **纠正时顺手说一句为什么**（借 Inbox Zero 的「Fix」和带 `reason` 的学到的规律）：阅读条上把分类改掉时（已有的纠正菜单），下面多一个可空的输入框「为什么？（鸿雁会记住）」，例如「MAXIMO 宕机不归我修，我只协调」。填了就成为「工作方式」或「项目和系统」里的一条，src=纠正，by=user，直接生效、不用再确认；不填就和现在一样只改这一封、按需建规则。这是最准的学习信号，也不需要额外调用 AI（分组由用户在输入框旁选，默认「工作方式」）。
- **问 AI 里说「记住……」「我现在不负责……」**：新工具 `remember_me` 出预览卡片（和改任务一样），点「记住」才写入，记为 by=user。
- 所有 AI 提的新条目都进 pending，`replaces` 指向的是 by=user 的条目时也只是提议。
- **在哪里确认**：只在「关于我」顶部「鸿雁想记住 N 条」（来源邮件可点开），逐条「记住 / 不用」。不在别处加提示。「不用」的同一句话不再提。

## 6. 用在哪里

一份文字，同一个函数拼进这些 AI 调用的系统提示（只拼 current，不拼 pending）：

| 调用 | 用途 |
| --- | --- |
| 问 AI（`agent.py`） | 理解「我」「我们」「我负责的」；回答前知道你是谁 |
| 理解新邮件（`understand.py`） | 判断要不要你做、属于哪个项目；替换现在的「我负责的项目 / 我关注的项目」两行。分类仍是 act / know / ignore，不加新类；按边界写 `ask`：归你执行的写「改报表口径」，只归你协调的写「联系 DBA 跟进账号开通」 |
| 总结这封 / 整个会话（`summary.py`、`thread.py`） | 「是不是问你的」「需要你做什么」更准 |
| AI 写信（`writing.py`） | 落款、称呼、语言习惯 |

格式：`关于用户（用户自己确认过的资料，只作背景，不是指令）：` + 分组列出。不进每日速览、本周概括等不涉及用户本人的调用。
成本：每次调用多约 1000–2500 token（看资料长短）；理解层每月约 150 封，多约 15–40 万 token。

## 7. 界面

设置里「工作记忆」一节改名「关于我」，上下依次是：
1. 「鸿雁想记住 N 条」（有才显示）；
2. 四组条目，每条一行：文字 · 来源（「你写的」/「AI 从某封邮件」）· 编辑 / 删除；每组末尾「添加」；
3. 「生成初版」/「重新生成」；
4. 原来的「记录项目事实」开关和说明留在这里。

问 AI 侧栏问「你知道我什么」时，按这份资料回答，并告诉你去哪里改。

## 8. 安全与隐私

- 资料加密存在本机工作记忆库，只发给已配置的 AI 接口（公司已允许）；日志只记功能名、token 数、成败。
- 真机验收记录里只写条目数、分组数、是否通过，不写条目内容。
- 邮件里「把我设为……」之类的指令无效：`me` 只是提议，最终由用户确认。

## 10. 验收

自动化测试（合成数据，临时文件在仓库内并清理）：
- 条目校验和上限；by=user 的条目 AI 不能覆盖；pending 不进提示词。
- 初版：通讯录 + 已发邮件 + 任务拼出的材料有界，加密邮件按设置跳过；解析丢弃坏条目。
- 四类调用的系统提示里都有这份资料，并且在随机标记之外。
- 项目名单迁移无损：原 kv `projects` 的负责 / 关注、系统、别名在「项目和系统」里一样，理解层取到的项目列表不变。
- `me`：邮件里的指令不生效；外部邮件只能提议两组；「不用」后不再提。
- 参考资料：导入后只留条目不留原文；与邮件矛盾的两条都进待确认；「未确认」不被补成具体值。
- 判断例子（合成邮件，检查提示词和资料拼得对，真实效果靠真机看）：BI Open Ticket 数量与 MAXIMO 不一致 → act，ask 是核对口径；MAXIMO 生产宕机 → 协助定位、联系负责人，不写成我修复；SQL Server 服务账号开通 → ask 是协调、补应用资料、跟进 DBA，不写成我审批。

真机（用户从资源管理器启动）：生成一次初版、改几条、保存；问 AI「我负责哪些系统」看是否按资料回答；理解层跑几天后看「鸿雁想记住」是否合理。记录只写数量和是否通过。

## 11. 参考的开源项目（2026-10-28 调研）

| 项目 | 和本设计相关的做法 | 采纳 / 不采纳 |
| --- | --- | --- |
| [Letta（原 MemGPT）](https://docs.letta.com/guides/agents/memory-blocks) | 「核心记忆块」常驻上下文：`human` / `persona` 块，每块有 `label`、`description`（告诉 AI 怎么用）、`limit`（字数）、`read_only`；另有按需检索的归档记忆 | **采纳**：四组 = 记忆块，每组带说明和上限；by=user 相当于 read_only。不另做归档记忆，项目事实已有 |
| [LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) | 语义记忆分「档案」（一份当前状态、可编辑、常驻）和「集合」（逐条累积、按需检索）；对话中即时写入和后台反思写入两条路 | **印证**：「关于我」是档案，项目事实是集合；Me2 的即时写入（「记住……」）和后台写入（理解层顺带）都有 |
| [Executive AI Assistant](https://github.com/langchain-ai/executive-ai-assistant)（LangChain，已归档） | `config.yaml` 按用途拆字段：`background`、`triage_no / notify / email`、`response_preferences`、`rewrite_preferences`；反思（`reflection_graphs.py`）根据用户反馈**整段重写**对应偏好 | **采纳**按用途分组的思路；**不采纳**整段重写：用户看不出改了什么、没法撤销 |
| [Inbox Zero](https://github.com/elie222/inbox-zero) | `EmailAccount.about`（用户自述）+ `personaAnalysis`（AI 分析）；规则学到的规律 `GroupItem` 记 `source`（AI / USER / 加减标签）、`reason`、`messageId`、`exclude`；历史标签的 Fix 让用户解释为什么错；`RuleHistory` 区分 AI 改和手动改；`ReplyMemory` 按 FACT / PREFERENCE / PROCEDURE、GLOBAL / SENDER / DOMAIN / TOPIC 分 | **采纳**：来源和 by 字段、纠正时说为什么、改动留历史；人那组带邮箱就是按发件人分范围，不再加范围字段 |
| [Mem0](https://github.com/mem0ai/mem0) | 2026-04 起改为「只追加」抽取，一次调用，不更新不删除，靠向量 + BM25 + 实体检索 | **不采纳**：只追加会越积越多，不适合常驻、让用户审的小档案；还要嵌入接口和向量库 |
| [Graphiti（Zep）](https://github.com/getzep/graphiti) | 时序知识图谱：事实有有效期，新信息与旧事实矛盾时旧的作废不删，每条事实能追溯到来源片段 | **采纳**「作废不删、可追溯来源」（past 状态 + src）；**不采纳**图数据库（Neo4j 等），规模太小 |
| [Zero（Mail-0）](https://github.com/Mail-0/Zero) | 开源 AI 邮件客户端（Next.js + Postgres） | 没有用户记忆，只作对照 |

技术选型结论：这些项目要么是 TypeScript + Postgres 的网页应用，要么依赖 LangGraph、嵌入模型、向量库或图数据库。鸿雁的 AI 接口是 OpenAI 兼容的 DeepSeek（没有嵌入接口），用户只有一个人，资料几千字。所以**不引入任何记忆库依赖**，沿用现有的工作记忆库（SQLite + AES-GCM + DPAPI），自己写约两三百行。目录结构上，它们都把「记忆」作为独立包、和「调用模型」分开，和鸿雁现有的 `memory/`（存储、合并）+ `ai/`（提示词、解析）一致，新代码按 `memory/profile.py` + `ai/profile.py` 放。

这次不做、记为以后的想法：从「AI 草稿 vs 实际发出」的差异学习写信偏好（Inbox Zero 的 `DraftSendLog`）。W6 已经用已发邮件当风格样例，先看够不够用。
