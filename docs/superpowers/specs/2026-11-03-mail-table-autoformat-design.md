## 2. 现状问题与根因

| 用户看到的问题 | 根因（代码里实际的做法） |
| --- | --- |
| 普通数据行被当成表头 | `tidyTable` 无条件把第一行设为表头，不看内容 |
| `23 台`、`SAR 2,500`、`N/A` 让整列失去对齐 | 一列里**每个**非空格都要匹配严格数字正则才右对齐；不认单位、货币代码、缺失值 |
| 列宽不合理 / 某列太宽 / 短数字被折行 | 粘贴时**无条件删掉所有列宽**交给浏览器自动排；「不折行」「加宽」用的是 `white-space`、`min-width`——**Outlook（Windows）两者都不支持** |
| 视觉普通 | 只有一套固定参数，没有按表格类型区分；数字没有等宽数字，没有分组行、标题行的样式 |
| 有业务含义的颜色被覆盖 | 表头行无条件刷成浅灰；`setRowKind` 换行类型时清掉底色；样式切换会重置边框 |
| AI 结果不稳定、只看头尾 | 每次都重新问 AI、无缓存；只发前 30 行和后 5 行；AI 只能回表头 / 合计 / 对齐 / 宽窄四样 |
| 手动改过的格式被下一次优化覆盖 | 没有记录哪些是用户亲手设的 |
| 发出后和编辑器里不一样 | 编辑器里有虚线辅助线；发送时不做邮件兼容转换（无 `align`/`bgcolor`/`width` 属性） |
| 加密邮件的纯文本部分表格糊成一串 | `html_to_text` 不在单元格之间加分隔：`1` 和 `53.91` 变成 `153.91`（已复现） |
| 可能动到不该动的表格 | AI 按钮按「正文里签名和引用之外的所有表格」找目标；从引用里拖出来的表格、编辑中移动过的表格也会被当成用户的表 |

**根本原因**：现在是「看到一种情况加一条样式规则」，规则直接改 DOM 样式，中间没有「这张表是什么结构、每列是什么类型」的模型；识别、排版、渲染、邮件兼容混在一起，所以每加一条规则都可能误伤别处，AI 也只能在样式层面打补丁。

## 3. 方案总览

参照 CKEditor（来源识别 + 小过滤器）和 Great Tables（结构模型 + 渲染分离），把表格处理改成一条清楚的流水线：

```
剪贴板 HTML
  │ ① 解析清理（按来源：Excel / WPS / Word / 网页 / 普通）
  ▼
表格模型 TableModel ── 每格：文字、原始值(x:num)、数字格式、合并、用户格式（有意义的）
  │ ② 分析：结构（标题行 / 表头层级 / 分组行 / 汇总行 / 备注行）＋ 列类型（加权投票）
  │    ↑ AI（可选）只修改「分析结果」，不碰 HTML
  ▼
排版方案 Layout ── 每列对齐、宽度(px)、是否折行；每行角色；主题参数
  │ ③ 渲染：编辑器里的表格（行内样式 + data-hy-* 记录）
  ▼
编辑器表格 ── 用户手动调整（记为「用户锁定」，以后的自动 / AI 优化不覆盖）
  │ ④ 发送时邮件兼容层：align / valign / bgcolor / width 属性、去掉 data-hy-*、纯文本部分用制表符分隔
  ▼
发出的邮件 HTML
```

**核心原则落到实现**：
- 分析和排版**只产生方案**，渲染时**只写样式和属性**，单元格内容（子节点）从不重建；每次优化前后比对「内容指纹」（逐格文字 + rowspan/colspan + 行列数），不一致就放弃这次优化并保留原样。
- 识别没把握就保守：例如表头置信度不够就不设表头，类型不到 90% 就按文本处理。
- 用户手动设过的东西（对齐、宽度、行角色、底色）记在单元格 / 行上，自动和 AI 都跳过。

## 4. 放在哪里、目录怎么分

**分析和排版放在页面 JS**（粘贴要瞬间出结果、列宽要用 Chromium 实测文字宽度），**纯函数部分不碰 DOM**，可以用 node 跑单元测试（沿用现有 `test_commands.py` 的做法）；**Python 后端**只负责 AI 调用、偏好存储、发送时的纯文本转换。

新建 `coremail_desktop/app/web/table/`（页面脚本仍是普通 `<script>`，不引入打包工具）：

| 文件 | 职责 | 依赖 DOM |
| --- | --- | --- |
| `table/source.js` | 识别来源（Excel / WPS / Word / Google Sheets / 网页），解析剪贴板 HTML：内联 `<style>`、**读出 `x:num` 和 `mso-number-format`**、去 `mso-*`、换算单位、处理片段标记 | 是（DOMParser） |
| `table/model.js` | DOM 表格 ↔ 表格模型（网格、合并、每格的文字 / 原始值 / 格式 / 用户锁定）；内容指纹 | 只在转换函数里 |
| `table/types.js` | 单元格和列的类型识别（§6.3），纯函数 | 否 |
| `table/structure.js` | 结构识别（§6.2），纯函数 | 否 |
| `table/layout.js` | 列宽算法（§6.5）和主题参数（§6.6），纯函数；文字宽度由调用方传入的测量函数提供 | 否 |
| `table/render.js` | 把方案写到编辑器表格上（只写样式 / 属性 / data-hy-*） | 是 |
| `table/mail.js` | 发送前的邮件兼容转换（§6.9） | 是 |
| `table/controller.js` | 管哪些表格归我们处理（粘贴 / 插入时登记 `data-hy-table`，自动和 AI 只处理登记过的表）、编辑后的失效与重新分析、撤销 | 是 |

**表格模型**用「占位网格」引用真实的单元格（合并格在它覆盖的每个位置都指向同一个格，不另造格子）；每格的分析结果和内容分开存；每个格式属性记来源：原表 / 主题默认 / 偏好 / AI / 手动。每行每列有稳定编号，AI 回复按编号对应，表格被改过就作废旧回复。

现有代码的去向：`app.js` 里的 `inlinePastedStyles` / `tidyTable` / `restyleTable` 等移进上面的文件；`compose.js` 只留表格菜单和按钮；`ai.js` 只留 AI 入口；后端 `ai/tables.py` 改为收发新的分析结构；`mime/sanitizer.py` 的 `html_to_text` 修表格分隔。

## 6. 各部分设计

### 6.1 解析与格式分类（需求 5）

把 Excel 带来的格式分成三类：

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 环境格式（丢） | 字体族、字号、行高、固定宽高、`mso-*`、默认黑色文字、白色底、Excel 默认细黑网格线 | 去掉，由主题接管 |
| 业务格式（留） | 非白色的单元格底色、非黑色的文字颜色、加粗 / 斜体 / 删除线、单元格内显式对齐（非 General 默认） | 保留，记为「来自原表」，主题不覆盖 |
| 结构提示（用） | 整行同一种填色、整行加粗、上粗下细的边框、合并单元格 | 不直接保留样式，而是作为 §6.2 结构识别的信号（例如整行加粗 + 首行 → 表头可能性高；上边框加粗 → 汇总行） |

判断「是不是默认」：整张表只有一种底色且覆盖表头行 → 当作表头样式（交给主题）；只在少数格出现的颜色 → 业务格式。**判断不了的底色一律保留**（保守）。

原表的颜色和加粗在格上另存一份（`data-hy-src`），换主题、关掉「保留原表颜色」都能恢复，不会因为一次排版永久丢失。

### 6.2 结构识别（需求 1）

每行打分，得到行角色：`title`（标题）、`head`（表头，可多行）、`group`（分组行）、`data`、`subtotal` / `total`、`note`（备注）、`blank`。

- **表头起点**：借鉴 messytables / frictionless——第一个「非空格数 ≥ 常见行宽 − 1」的行；它上方只占一两格（或横跨整表的合并格）的行是标题行。
- **是不是表头**（不再无条件）：比较候选行和下面数据行的类型——候选行是文字、下面同列是数字 / 日期 → 加分；候选行加粗 / 有底色 → 加分；候选行和数据行类型一样（例如都是文字清单）→ 减分。分数不够就**不设表头**（保守）。
- **多行表头**：表头行里有横向合并（跨列）的，下一行也算表头，直到遇到第一行数据类型的行，最多 3 行。
- **分组行**：数据区里只有第一格有字（或一个横跨整行的合并格）、其余为空的行。
- **汇总行**：第一个有字的格匹配 合计 / 小计 / 总计 / 共计 / 平均 / Total / Subtotal / Sum / Grand Total，或原表上边框加粗 + 加粗；或位于最后、文字列为空而数字列有值。
- **备注行**：数据区之后、只有一格有长文字（以 注 / 备注 / 说明 / Note / * 开头更确定）。
- 空行、空列：保留（不删），不参与类型投票，渲染时压低高度。
- 每个判断带置信度；**允许「不确定」**——不确定的行按普通数据行排，不加表头 / 汇总样式。汇总行里可以既有文字也有数字，按格记录例外。

### 6.3 类型识别（需求 2）

**先用原表告诉我们的**：`mso-number-format` 含 `%` → 百分比、含 `yyyy`/`m/d` 等 → 日期、含货币符号 → 金额、`@` 或 `"0000"` 这类补零格式 → 文本 / 编号；有 `x:num` 说明 Excel 存的是数值。这些在 CSSOM 内联**之前**用声明解析器从原始 `<style>` 文字里取出（CSSOM 会丢 `mso-*`）。`x:num` 只是证据，**显示的文字永远不改**；数值也可能是日期、编号、金额。没有这些信息（WPS、网页、手打的表）时才解析文字。

**编号证据优先于「能当数字解析」**：前导 0、固定位数、电话格式、列名是 编号 / 编码 / 电话 / ID、文本格式或补零格式——有任何一条就按编号，不按数值。日期写法有歧义（如 `03/04`）时保持不确定，不强行判断。

单元格类型（每种一个解析器，借鉴 frictionless 的 fields/）：`empty`、`missing`（`N/A`、`-`、`—`、`/`、`无`、`TBD`）、`int`、`decimal`、`money`（`¥ $ € £` 和 `SAR USD RMB CNY EUR` 等代码，前后都可）、`percent`、`date`、`time`、`datetime`、`quantity`（数字 + 单位：`台 个 件 套 人 天 小时 h kg m 米 GB`…）、`id`（编号 / 编码 / 电话 / 身份证 / 工单号：有前导 0、长度 ≥ 8 且无千分位、字母数字混合、带 `-` 分段的数字、列名含 编号 / 编码 / 号 / ID / No / 电话 / Tel）、`status`（短文本且整列取值种类少，如 已完成 / 进行中 / 正常 / 异常 / Yes / No）、`text`、`longtext`（>30 字或含换行）。

**列类型**：借鉴 frictionless 的置信度——`missing` 和 `empty` 不计；某类型占剩余格 ≥ 90% 才认定；数字族（int / decimal / money / percent / quantity）可以互相合并为「数值列」；都不够就是 `text`（保守）。表头文字也参与（如「金额」「日期」「编号」）。

| 列类型 | 对齐 | 折行 | 其他 |
| --- | --- | --- | --- |
| 数值（含金额、百分比、带单位数量） | 右 | 不折 | 等宽数字（`font-variant-numeric: tabular-nums`，不支持的客户端无影响） |
| 日期 / 时间 | 居中 | 不折 | — |
| 编号 / 电话 / 序号 | 居中（短）/ 左（长） | 不折 | 不当数字处理 |
| 状态 | 居中 | 不折 | 保留原表颜色 |
| 文本 | 左 | 可折 | — |
| 长文本 | 左 | 可折 | 分到更多宽度 |

表头单元格跟随本列对齐；跨列的分组表头居中。

### 6.4 用户锁定与再次优化（需求 1 原则、需求 6）

- 用户在右键菜单里改的对齐、宽度、行角色、底色，记在格 / 行上（`data-hy-lock="align width role fill"`）。之后粘贴整理、AI 优化、换主题都跳过这些项。
- 「AI 优化这张表」「重新自动排版」只改没锁定的部分；菜单里加一项「清除我的调整」解锁（不加别的新入口）。

### 6.5 列宽算法（需求 3，本次重点）

用 canvas `measureText` 实测文字宽度（和编辑器同字体，比反复排版 DOM 快），按列算（只统计普通数据行和表头，跨列的标题 / 备注格不进单列统计）：
- `min`：最长的一个「不可断开的片段」（数值 / 日期 / 编号整格，文本按词或单字）+ 左右留白和边框；
- `max`：最长一格不折行的宽度 + 留白和边框。

可用宽度 `W` = min(编辑器正文宽度, **640px**)（常见邮件阅读宽度，Outlook 预览窗、Gmail 网页都能完整显示），下限 360px。跨列的格宽度 = 所占各列之和，并作为约束参与分配。

1. 不折行的列（数值、日期、编号、状态、短文本）给 `max`；
2. 如果总和 ≤ `W`：可折行列也给 `max`，表格宽度 = 实际总和（**不撑满**，避免稀疏）；
3. 否则剩余宽度按可折行列的 `max` 开方加权分配，每列不小于它的 `min` 和 120px（中文约 8 个字）、不大于 360px——**少量超长文字不会把整张表拉变形**；
4. 如果连不折行列的 `max` 之和都超过 `W`（列很多的宽表）：**不硬压、不缩字、不隐藏列**，按内容需要的宽度输出，同时把可折行列压到 `min`。编辑器里给这种表套一层可横向滚动的外框（只在编辑器里，发送时去掉），收件人那边由客户端自己处理。

输出（为 Outlook）：每列宽度写成**像素**，写在**每一格**的 `width` 属性和 `style="width:…px"` 上（跨列格写各列之和）；表格 `width` 属性 + `style="width:…px;max-width:100%"`。「不折行」用 `nowrap` 属性 + `white-space:nowrap`（Outlook 认属性）。不再用 `min-width`。这些只是提示，内容太长时客户端仍可能撑开，所以宽表靠第 4 步保证可读。

### 6.6 视觉与主题（需求 4）

借鉴 Great Tables：主题是一组扁平参数（字号、行距、上下 / 左右留白、表头底色 / 文字色 / 字重、行分隔线颜色、外框线、汇总行上边线、分组行底色、斑马纹、数字字体），预设只是不同取值。全部十六进制颜色（Outlook 不认 rgba）。

| 预设 | 场景 | 要点 |
| --- | --- | --- |
| 简洁商务（默认） | 大多数邮件 | 表头浅灰底 + 深色字 + 下粗线；行间极浅横线；无竖线；留白 7px×12px；汇总行加粗 + 上细双线感（2px） |
| 紧凑数据 | 行多列多的数据表 | 留白 4px×8px；略小字号（不小于正文 −1px）；斑马纹代替行线 |
| 正式报告 | 发给客户 / 领导 | 上下外框粗线、表头上下线（三线表风格）；表头不填底色；分组行小号加粗 |

默认根据表格自动选：行数 > 20 或列数 > 8 用「紧凑数据」，其余「简洁商务」；用户在菜单里选过的记为偏好（§6.8）。

分组行：浅底色 + 加粗，横跨整行；备注行：小一号、灰色字、不加线；标题行：加粗、稍大、无底色、和表格之间留空。

### 6.7 AI 深度优化（需求 6）

- **AI 改的是分析结果，不是样式**：发给 AI 的是本机的分析（每行角色、每列类型、置信度、合并关系）+ 单元格文字；AI 只回对**语义**的修改，用行 / 列编号指明：某行改角色（标题 / 表头边界 / 分组 / 小计 / 合计 / 备注）、某列的含义和类型、表格用途（费用表 / 统计表 / 任务跟踪 / 参数说明 / 清单）、建议预设、需要强调的列，每项带置信度。**宽度、颜色、留白、HTML 一律由本机决定**（W8 里让 AI 回「宽窄」是不对的，去掉）。本机校验：未知编号、和合并关系冲突的、表格已被改过的（指纹不符）一律丢弃。AI 结果和本机按同一套排版、渲染输出——所以 AI 也逃不出内容安全的约束，风格和本机一致。
- **大表**：不再只发头尾（会漏掉中间的分组和小计）。发「结构摘要」：所有行的本机摘要（角色、非空格数、类型签名，一行一个短串），再加代表行的全文——开头和结尾、所有结构候选行（疑似表头 / 分组 / 小计 / 备注）、类型异常的行、中间均匀抽样；按总 token 预算控制，不只按每格字数。
- **稳定**：温度 0 不够。接受过的 AI 方案按「内容指纹 + 合并结构 + 相关偏好 + 分析器版本 + 模型」缓存在本机（后端 `ai/tables.py`），重复点击直接复用；菜单里「让 AI 重新考虑」才重新请求。AI 结果只在本机置信度低的地方生效；本机置信度高的结论，AI 要改须给出理由，否则忽略。
- 入口不变：写信「AI」按钮（正文只有表格时只优化表格）和右键「AI 优化这张表」；可撤销。

### 6.8 学习偏好（需求 7）

最简单、可预测的做法——**只从用户明确的手动操作里学，不做隐式推断**：
- 用户在菜单里改「表头对齐」「日期对齐」「预设」「疏密」「保留原表颜色」；**在两张不同的表上做了同样的选择**，提示条上出现一次「以后粘贴的表格都这样？」（一个按钮，不是弹窗）；点了才记为偏好。一张表上的特殊调整不会变成全局规则。
- 设置 → 写信里一个「表格」小节：列出这几项当前值，可改，可「恢复默认」。不加别的界面。
- 存在本机加密缓存（和其他偏好一样，带格式版本号），不上传。恢复默认只影响以后粘贴的表格，不改已写好的邮件。

### 6.9 邮件兼容（需求 8）

依据 Can I Email 数据（Outlook Windows：不支持 `min-width`、`white-space`、`rgba`、`table-layout`；`width`、`text-align`、`padding`、`max-width` 部分支持）：

发送前（`outgoingHtml` 里调用 `table/mail.js`）对正文里的表格：
- 照 juice 的做法补老式属性：`align`、`valign`、`bgcolor`、`width`（像素）、`nowrap`、`cellpadding="0" cellspacing="0" border="0"`；
- 边框统一写成每边的简写 `border-bottom:1px solid #xxxxxx`（Outlook 对简写支持最好）；
- 去掉 `data-hy-*`（编辑器专用）；
- 纯文本部分（加密邮件的 text/plain）：`html_to_text` 在单元格之间加制表符、行尾换行，修复「153.91」。

### 6.10 撤销

粘贴整理：先插入原表（仅内联样式），再把排好的表整张替换进去，两步都走 `execCommand('insertHTML')`，都进 Chromium 自己的撤销记录——Ctrl+Z 一次回到「未整理的原表」，再一次回到粘贴前；提示条「已整理表格 · 撤销整理」。直接改 DOM 不进原生撤销记录，所以 AI 和菜单操作也用「整表替换」的方式写回，和打字、输入法的撤销不打架。

### 6.11 编辑之后

用户改了某格文字：只重新判断这一列的类型（不重排整张表，不打断输入）；增删行列：作废缓存的 AI 方案，结构按当前内容重新识别，手动锁定保留。发送时从**当前编辑器内容**单独渲染一遍发送用 HTML，绝不从模型重建单元格文字。

## 8. 测试与验收

- **样例库** `tests/fixtures/tables/`：12 个场景 × 剪贴板 HTML（合成数据，含合并、颜色、单位、缺失值、超长文字、宽表、200 行大表）。
- **内容不变**（每个样例必测）：优化前后逐格文字、rowspan / colspan、行列数完全一致。
- **识别正确**：每个样例写下期望的行角色和列类型，node 单测比对。
- **兼容规则检查**：发送 HTML 里没有 `rgba`、`min-width`；每个有对齐的格都有 `align` 属性；有宽度的列有像素 `width` 属性。
- **看效果**：`tools/` 加一个脚本，用 Qt WebEngine 把 12 个样例的优化前 / 后渲染成一张对比图（编辑器宽度 640px 和 420px 两种），供人工评审；保存在 `docs/releases/` 的记录里。
- **性能**：200 行 × 20 列粘贴整理 < 150ms。
- **稳定**：同一输入跑两次输出 HTML 完全相同。
- **操作链**：粘贴 → 改字 → AI → 手动调整 → 撤销 / 重做，每步之后内容指纹不变；签名和引用里的表格始终不被碰到。
- **收件人实测**：编辑器截图证明不了 Outlook / Gmail 的效果。P6 把样例真正发给自己，在 Outlook（Windows）、Gmail 网页、Coremail 网页，正常宽度和窄窗口、深色模式下各看一次，按评审表打分（层次清楚、无截断重叠、宽度合理、重点保留），不追求各客户端像素一致。
