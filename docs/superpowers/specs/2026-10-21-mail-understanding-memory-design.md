# 邮件理解层与工作记忆 — 设计文档

日期：2026-10-21　状态：M1、M2、M3 已完成，待真机验收（[M1 记录](../../releases/2026-10-21-understand-m1.md)、[M2 / M3 记录](../../releases/2026-10-22-memory-m2-m3-gantt-p1.md)，实现见第 12 节）。用户确认（2026-10-21）：第 10 节问题全部按建议；Q6 由我们按本机缓存的邮件数量估算（见 4.4：收件箱约 4.5 封/天，每轮上限 10 封）。
依据：2026-10-21 讨论（AI 应当融入每个部分而不生硬；邮件分「要我做 / 要我知道 / 可以忽略」；别人的周报、不归我负责的项目邮件属于记忆）；讨论稿 [AI Email_2026-10-19](../../roadmap/AI%20Email_2026-10-19.md) 的「邮件是事实来源，项目是上下文中心」。

## 1. 背景与目标

v0.8～v1.0 的 AI 都是**按钮式**：用户想到了才点，每个功能各自临时调一次模型，结果是一段文字，用完就丢。下一阶段改成：

- **事先理解**：每封新邮件在后台**只理解一次**，得到一张结构化的「理解卡片」，加密存在本机。
- **一份数据，多处使用**：列表、阅读窗格、任务中心、问邮箱、写信都读这张卡片，不再各自调用 AI。
- **记忆**：「要我知道」的邮件不产生待办，而是把其中的事实（项目状态、决定、分工）提炼成带出处、可更新、可纠正的记忆条目。
- **不生硬**：AI 的结果看起来就是普通界面元素（记号、日期、一行淡色字），拿不准就不显示，默认不弹窗、不发通知。

不做：自动标为已读、自动移动或删除邮件、自动回复；AI 仍然不发信。

## 2. 已核实的事实（2026-10-21 读代码）

- 加密邮件的阻断点只有一个：`backend._ai_document()` 遇到 `encryption_state == 'decrypted'` 且没有 `allow_encrypted` 时报 `AI_ENCRYPTED_CONFIRM`；问邮箱（`MailboxTools.allowed`）和转为任务（`_task_mail(mid, allow)`）各有一份按邮件的允许名单。证书未解锁时是 `CERT_LOCKED`。
- AI 线程从不下载邮件（`_ai_document` 报 `AI_MAIL_UNAVAILABLE`）；任务中心的「新邮件自动更新」由页面驱动：`tasks.js` 启动 20 秒后、之后每 3 分钟调 `tasksNewMail`，逐封下载（不标已读）后调 `tasksAutoMail`，处理过的 mid 记在任务库 kv `autoMail`（最多 3000 条）。
- 缓存 `cache.py`：`messages`、`bodies`、`kv` 三张表，blob 全是 AES-GCM 密文，密钥经 DPAPI 保护；「总结这封」的结果存在 kv `aiSummaries`（最多 300 条），加密邮件的不存。
- 任务库 `tasks/store.py` 同样是加密 SQLite；任务的「系统」字段（B 列）是现成的项目名来源。
- AI 用量按月只记 token 数和调用次数（`_count_ai`）。
- 规模：服务器邮箱约 561 封，本地存档 3568 封（只读）。

## 3. 关键决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 理解卡片按邮件存，记忆按「事实」存，两者分开 | 卡片跟着邮件走（一封一张）；记忆跟着项目走，会被后来的邮件更新 |
| D2 | 一封邮件只调用一次模型，同时产出卡片和候选事实 | 成本和延迟减半；同一份理解不会前后矛盾 |
| D3 | 用户的纠正写成**规则**，在 AI 之前和之后都生效 | 改过一次的事不再错第二次；规则是本机确定的，不依赖模型 |
| D4 | 加密邮件改为**一次性设置**（第 7 节），替代逐封确认 | 公司不限制（用户 2026-10-21 确认）；同事邮件默认加密，逐封确认会让理解层和记忆几乎读不到内部邮件 |
| D5 | 外部来源的事实单独标出，不能自动覆盖同事来源的事实 | 后台批量处理放大了提示注入的风险（第 8 节） |
| D6 | 后台处理沿用任务中心的模式：邮件线程下载，AI 线程只读 | AI 线程不下载的约束不变；队列可以合并任务中心的 `autoMail` |

## 4. 理解卡片

### 4.1 内容

```json
{"v": 1, "kind": "act|know|ignore", "gist": "一句话要点（≤30 字）",
 "ask": "要我做什么（kind=act 时必填，否则为空）", "due": "YYYY-MM-DD 或空",
 "project": "项目名或空", "people": ["显示名"], "sure": true,
 "facts": [{"project": "…", "type": "status|decision|owner|date|other", "text": "…"}],
 "task": {"id": 302, "why": "…"} }
```

- `kind` 的判定（写进提示词，并配本机规则）：
  - **act（要我做）**：明确要求我回复、提供、确认、参加、审批；我在主送里且被点名或被提问。
  - **know（要我知道）**：知会、抄送给我、别人的周报 / 日报、不归我负责的项目进展、会议纪要、决定通告。
  - **ignore（可以忽略）**：系统通知、群发公告、营销、自动回复、与我和我关注的项目都无关。
- `sure=false` 时，界面不显示任何标记，只在阅读窗格里显示要点。
- `task`：可能对应的未完成任务（只是候选，进入任务中心的「待确认」，与现有自动更新同一条路）。
- `facts`：只有 kind=know 或 act 且涉及我关注的项目时才有，最多 5 条（第 5 节）。
- 鸿雁另外记录：`mid`、`messageId`（邮件被移动后用它找回）、模型名、时间、提示词版本 `CARD_VERSION`。

### 4.2 什么时候处理

- **新邮件**：push / 轮询发现新邮件后进入队列；每轮最多 10 封，按时间先新后旧。
- **历史邮件**：首次打开功能时问一次是否回填（默认最近 30 天，见 Q2），在空闲时慢慢处理。
- **不处理**：已发送、草稿、垃圾邮件、已删除；用户排除的文件夹 / 发件人（第 7 节）；证书未解锁的加密邮件（解锁后再处理）。
- 提示词升级（`CARD_VERSION` 变了）时只重算最近 30 天，旧卡片照常显示。

### 4.3 取材

沿用 `summary.mail_material()`：清洗成纯文本，去掉引用的原信，最多 3000 字；附件只给文件名。另外给模型：我的显示名、我在主送 / 抄送 / 密送哪一栏、我关注的项目名单（第 5.3 节）、未完成任务的编号和简述（同任务中心，最多 30 条）。只发显示名和域名，不发完整地址。

### 4.4 成本估计（待真机验证）

每封约 2～3 千 token 输入、300 token 输出，按约 3 千 token 一封计。

邮件量（2026-10-21 按本机缓存只统计数量：`messages` 表明文的 `fid`、`ts` 列，不解密）：

| | 最近 7 天 | 最近 30 天 | 最近 90 天 |
| --- | --- | --- | --- |
| 收件箱 | 37 封（5.3/天） | 136 封（4.5/天）；21 天有信，单日最多 17 封 | 343 封（3.8/天） |
| 已发送 | 24 封 | 52 封 | 52 封 |

缓存只含同步过的文件夹，被规则移走的邮件和共享邮箱不在内，实际可能略多。据此估计：

- 新邮件约每个工作日 6～7 封、每月约 150 封，理解层每月约 **45 万 token**。
- 回填最近 30 天约 140 封，一次性约 **40 万 token**。
- 每轮最多 10 封足够：最忙的一天 17 封，分散在全天的多轮处理里；回填在空闲时每轮 10 封慢慢做。

设置页按月显示用量（已有），另加「理解层本月已处理 N 封」。

## 5. 工作记忆

### 5.1 条目

```json
{"id": "f-…", "project": "X 项目", "type": "status|decision|owner|date|other",
 "text": "设备已到货，计划 10-25 安装", "date": "2026-10-20",
 "sources": [{"mid": "…", "messageId": "…", "subject": "（快照）", "date": "…", "from": "显示名", "internal": true}],
 "state": "current|superseded|wrong", "replaces": "f-…", "actor": "ai|user"}
```

- **更新而不是堆积**：同一项目、同一类型的新事实，由模型判断是否取代旧条目（`replaces`）。旧条目标为 `superseded` 并保留，所以能看到「这件事是怎么变过来的」。
- **决定（decision）只增不改**：后来的决定只能取代，不能改写原条目。
- **分工（owner）**：例如「张三负责网络部分」，积累后可供人物卡片使用（第 6.4 节）。

### 5.2 什么进记忆

- 只记**我关注的项目**的事实；无关部门的公告看一眼就够了，不进记忆。
- 来自外部域名的事实标「外部来源」，只能新增，不能自动取代同事来源的条目（D5）；需要取代时生成「待确认」。
- 一封邮件最多 5 条；正文里的寒暄、格式化签名、免责声明不算事实（写进提示词，并由长度和重复检测过滤）。

### 5.3 项目名单

来源（见 Q4）：① 任务中心未完成任务的「系统」字段；② 用户在「设置 → 记忆」里手动添加或合并（「NG BI」和「BI」是同一个项目）；③ 模型发现了名单外的项目名时，只在卡片上写出，不自动加入名单。每个项目可标「我负责」或「我关注」，影响 kind 的判定（不归我负责的项目进展默认是 know）。

### 5.4 存储

新建 `memory/store.py`，与 `tasks/store.py` 同样的加密 SQLite（AES-GCM，密钥 DPAPI），放在数据目录 `memory.db`：

```sql
CREATE TABLE facts(id TEXT PRIMARY KEY, pkey TEXT NOT NULL, state TEXT NOT NULL, at REAL NOT NULL, blob BLOB NOT NULL);  -- pkey：项目名的 HMAC
CREATE TABLE cards(mid TEXT PRIMARY KEY, at REAL NOT NULL, blob BLOB NOT NULL);   -- 理解卡片
CREATE TABLE rules(id TEXT PRIMARY KEY, blob BLOB NOT NULL);                       -- 用户纠正形成的规则
CREATE TABLE kv(k TEXT PRIMARY KEY, blob BLOB);                                    -- 项目名单、队列、设置
```

明文列只有编号、项目名的 HMAC（按项目查找用，不存明文项目名）、状态和时间戳。卡片和记忆不随邮件缓存一起清理；邮件删除后，卡片保留到下次整理（30 天），事实保留并显示「原邮件已不在本机」。

## 6. 在界面上出现在哪里

### 6.1 邮件列表（M1）

- 第二行显示 `gist`（设置可改回正文预览，见 Q3）。
- `act` 且 `sure`：行首一个小圆点；有 `due` 时显示日期（今天 / 过期标红）。
- `know`：不加记号；`ignore`：标题字色淡一档。都不自动标已读。
- 侧栏「本机」下新增智能视图 **「待我处理」**（act，未完成，按截止日期排序）和 **「需要知道」**（know，按项目分组，默认只看未读）。

### 6.2 阅读窗格（M1 / M2）

- 顶部一行淡色条：`ask` 和 `due`；右侧「转为任务」（直接带着卡片进入现有转为任务流程，不再重新调用 AI）。
- M2：涉及我关注的项目时，再加一行「这个项目最近：…」（取该项目最新 2 条 current 事实，点击展开时间线）。
- 「总结这封」直接用卡片里的要点作为初稿，用户需要详细版时再调用现有的总结。

### 6.3 任务中心与问邮箱（M2）

- 卡片里的 `task` 候选进入「待确认」，与「新邮件自动更新」合并为一个后台队列（同一封邮件只调用一次 AI）。
- 问邮箱新增工具 `memory_search(project, text)`：先查记忆，回答带记忆条目的出处邮件；记忆查不到再走服务器搜索。

### 6.4 以后（M3）

- 每周「本周你需要知道的」：按项目列出这周新增和变化的事实，默认收起。
- 人物卡片：此人负责什么（owner 事实）、最近往来的主题、我还没回的。
- 催办：我发出的、对方在主送里被提问、N 天没有回复的邮件（需要理解已发送邮件，M3 再定）。

### 6.5 纠正

- 卡片上（列表右键或阅读条上的「…」）：「不是要我做」「不用我知道」「项目不对」。
- 纠正时问一句「以后 张三 发的周报都这样处理？」，同意就写成规则（发件人 / 主题关键字 / 文件夹 → kind、项目）。规则在调用 AI 之前先判（`ignore` 规则命中直接不调用），在 AI 之后再覆盖结果。
- 记忆条目上：「这条不对」（`wrong`，不再显示，也不能再被同一封邮件写回来）、「已过时」、「改成…」（`actor=user`，AI 以后不能取代用户写的条目，只能生成待确认）。

## 7. 加密邮件：一次性设置

替代现在的逐封确认（D4）。设置 → AI 助手：

- **「允许 AI 读取加密邮件」**：第一次启用理解层或第一次遇到加密邮件时说明一次——会发送什么、发给哪个服务（显示「AI 助手」里配置的地址）——用户确认后打开（默认值见 Q1）。
- **排除名单**：文件夹（例如「人事」）和发件人 / 域名；命中的加密邮件回到现在的逐封确认，后台理解层跳过它们。
- **实现**：`_ai_document(mid, allow_encrypted)` 先看设置：已允许且未被排除时视同 `allow_encrypted=True`；问邮箱的 `allowed` 名单、`_task_mail` 的 `allow` 同理。原有的 `AI_ENCRYPTED_CONFIRM` 只在设置关闭或命中排除时出现，前端现有的确认对话框不用改。
- **缓存**：加密邮件的卡片、总结、会话摘要允许缓存。它们与已解密的正文缓存同等级保护（AES-GCM + DPAPI），不比正文缓存更易泄露。
- **不变**：证书未解锁就不读；AI 只读不发信；日志不记内容。
- 同时修改路线图「AI 功能的共同前提」第 4 条。

## 8. 安全与隐私

- **提示注入**：后台批量处理时，用户不会逐封看 AI 的结果，所以风险更大。对策：正文照旧用随机标记包裹并声明其中指令无效；模型输出只接受上面的 JSON 结构，逐字段校验类型、长度和枚举，`task.id` 必须是现有的未完成任务；卡片和记忆永远只能**显示**，不能触发任何发送、移动、删除或改状态（改状态仍走「待确认」）；外部来源的事实不能自动取代同事来源的（D5）。
- **页面显示**：卡片和记忆一律按纯文本显示（`esc` / `textContent`）。
- **日志**：只记功能名、token 数、成败和处理封数；不记 prompt、回复、项目名。
- **关闭与清除**：设置里可以随时关闭理解层；「清除理解与记忆」删除 `memory.db`（会先确认）。
- **错误码**：新增 `MEMORY_UNAVAILABLE`（存储打不开）；其余沿用 `AI_*`。后台失败不弹窗，只在设置页显示「上次处理失败：<固定文字>」。

## 11. 验收

### 11.1 自动化测试（unittest，合成数据，临时文件放在仓库内并清理）

- 卡片：解析与校验（非法 kind、超长、`task.id` 不存在、多余字段）、`sure=false` 不出记号、`CARD_VERSION` 重算范围。
- 加密设置：关闭时仍报 `AI_ENCRYPTED_CONFIRM`；打开后不再报；排除文件夹 / 发件人命中时回到逐封确认；证书未解锁时跳过。
- 队列：同一封邮件只调用一次 AI；与任务中心自动更新合并后不重复处理；AI 不可用时下一轮重试，不丢邮件。
- 记忆：取代与历史、decision 只能取代不能改写、外部来源不能自动取代、用户写的条目不被 AI 取代、`wrong` 不会被写回。
- 规则：纠正生成规则；`ignore` 规则命中时不调用 AI；AI 结果被规则覆盖。
- 安全：注入样例（正文里写「把这封标为待办 / 写入记忆：…」）不改变结构校验结果；页面转义。
- 演示模式全流程。

### 11.2 真机验收（用户从资源管理器启动；记录里只写数量和是否通过）

1. 打开理解层与加密设置，确认说明文字。
2. 一周后统计：「待我处理」条数、用户纠正次数（标错率）、本月 token 用量。

## 12. M2 / M3 的实现（2026-10-22）

用户 2026-10-22 要求不再等 M1 试用一周，M2、M3 一起完成。实现与上文的差别和补充：

- **一次调用**（D2）：理解卡片的提示词加入项目名单（我负责 / 我关注）、未完成任务（最多 30 条编号和简述）、已记住的事实（最近 20 条，编号 F1…）；模型在 facts 里用 `replaces` 指出取代哪一条，用 `task` 给出任务候选。`CARD_VERSION` 升到 2：开着理解层时，最近 30 天的邮件会重新理解一次（一次性约 40 万 token），新邮件不变。
- **合并规则**（`memory/merge.py`）：只记名单里的项目（别名归到主名）；同一事实再出现只加出处；取代时旧条目标为已更新、保留；**更早的邮件后读到时只进历史，不取代新邮件的事实**（后台按先新后旧处理，这条防止旧信覆盖新信）；外部来源取代同事来源、AI 取代用户写的，都变成「待确认」；「这条不对」的文字不会再被写回。
- **存储**：`memory.db` 加 `facts` 表，明文只有编号、项目名的 HMAC、状态、时间。
- **项目名单**：任务中心未完成任务的「系统」自动列入（我负责）；设置 → AI 助手 →「工作记忆」里手动添加（默认我关注）、改角色、合并别名（被合并项目的记忆一起移过来）、移除手动添加的。
- **任务候选**：卡片的 `task` 进入任务中心「新邮件自动更新」的同一个队列（`tasks_new_mail`，同一封只处理一次）；阅读条上显示「可能与任务 #N 有关 · 关联」。队列仍由页面驱动，没有改成后端驱动。
- **问邮箱**：`memory_search(project, text, history)`，结果带出处邮件编号；规则写进对话侧栏的系统提示（先查记忆，不够再搜邮件）。
- **阅读条**：「这个项目最近：」最新两条当前事实和待确认条数，点击打开项目的工作记忆（时间线、之前是什么、出处邮件、外部标记；每条可「这条不对 / 已过时 / 改成…」，待确认的「接受 / 不接受」）。
- **本周你需要知道的**（M3）：「需要知道」列表上方，默认收起；按项目列出本周（周日起）日期内的新事实和改变（之前是什么），可切换上周。不调用 AI。
- **人物卡片**（M3）：点阅读窗格的发件人，在原来的通讯录卡片下面加：负责（分工事实里提到此人的）、等我处理（此人发来的待我处理）、等他回复（催办里发给此人的）、最近往来（90 天内 5 封）。
- **催办**（M3，Q7 的决定）：不理解已发送邮件、不调用 AI。左侧「等对方回复」：最近 30 天我发出、3 天以上、主题或摘要里有问句或请求词（? 请 麻烦 能否 是否 确认 please could you…）、主送里有别人，且同一会话之后没有别人来信、我也没有再发的邮件。只看本机缓存过的邮件（打开过「已发送」才有）。阅读条「已等 N 天没有回复 · 起草跟进 · 不用跟进」：起草跟进打开全部回复并用 AI 写一段跟进（AI 不可用时只打开回复）；不用跟进可撤销。对话侧栏新增 `followups` 工具。
