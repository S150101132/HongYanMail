## 1. 背景与最终产品定位

### 1.1 当前情况

用户正在开发公司 Coremail 邮件的 Windows 桌面客户端“鸿雁”，希望逐步接入 DeepSeek，把大模型作为核心智能能力。同时，日常工作任务由 **ChatGPT Work 操作 Excel** 进行管理，任务可能来自邮件、会议、电话、现场沟通及个人安排。

现状存在两条相互独立的工作流：

- **邮件流**：收信、阅读、搜索、回复、附件、通讯录、加密签名等操作在鸿雁完成。
- **任务流**：向 ChatGPT Work 自然语言汇报进展，由其更新 `未完成任务.xlsx` 和 `已完成任务.xlsx`，维护历史、状态、依据，并借助 Git 追溯变更。

目标是使两条工作流**自然汇合**，使用户最终不再依赖手工维护 Excel。

### 1.2 已选定的产品方向 [讨论共识]

选择 **B：AI 原生工作助手**，并进一步选择 **“任务 + 项目融合工作台”**：

- **邮件**：沟通事实及原始证据；保留传统客户端的高速、高效操作。
- **事项（Task/WorkItem）**：工作的执行、责任、进展、依赖、验收和后续行动。
- **项目（Project）**：长期上下文、相关人员、决策、风险、事项集合。
- **AI（DeepSeek 为第一候选）**：理解意图、检索历史、抽取工作信号、关联项目/事项、形成建议并通过受控工具执行。
- **工作记忆**：保存可追溯且可纠正的长期信息，不依赖一次聊天 Session。

> 设计原则：**用户无需通过聊天才能使用邮箱；AI 应当随着当前邮件、任务、项目提供帮助，而不是在应用右侧常驻一个占空间的聊天窗。**

### 1.3 不追求的方向

1. 不直接照搬现有大型项目管理平台替换整个鸿雁。
2. 不把 DeepSeek 的会话历史等同于正式工作数据。
3. 不把每封邮件都自动转成任务。
4. 不允许 AI 不经确认擅自发信、增加对外收件人或改变重要已确认状态。
5. 不要求用户为了 AI 而放弃现有三栏阅读、会话、搜索、快速回复等成熟交互。

## 3. 核心产品交互

### 3.1 首页：今日工作台（Today Workspace）[讨论共识/建议]

首页不是“全屏 AI 对话”，而是**持续更新的行动视图 + 自然语言入口**。

```text
┌───────────────────────────────────────────────────────────────────────┐
│ 鸿雁       今日 | 邮件 | 事项 | 项目 | 智能检索 | 通讯录                 │
├───────────────────────────────────────────────────────────────────────┤
│ 今天先做什么？                                                        │
│ [询问工作、查找邮件、准备回复、分析项目........................]     │
│ [整理今天事项]  [本周项目变化]  [等待谁回复]                          │
├───────────────────────────────────────────────────────────────────────┤
│ 需要我处理        等待别人         待我审核/确认                      │
├───────────────────────────────────────────────────────────────────────┤
│ AI 推荐优先处理                                                       │
│  #302 CRM 网络连接受阻   [历史] [来源邮件] [准备跟进]                 │
│  #329 CRM LDAP 资料待提供 [历史] [联系客户]                            │
│  ...                                                                  │
├───────────────────────────────────────────────────────────────────────┤
│ 我的项目：CRM 部署 | NG BI 报表 | B/OSS | ...                         │
└───────────────────────────────────────────────────────────────────────┘
```

设计要求：

- 传统“邮件”页面保持已有三栏和操作习惯；AI 不应强制介入。
- 首页摘要明确区分**已核实任务状态**与**AI 待审核建议**；数量与优先级依据清晰。
- 点击事项进入详情和完整时间线；点击证据可以定位原邮件/附件。
- AI 不凭空编造截止日期、负责人、完成状态或“等待回复”的事实。
- 支持“只看我负责”“等待别人”“受阻”“按项目”等视图。

### 3.2 三层 AI 交互 [建议]

1. **内嵌上下文智能**：打开邮件时显示少量高价值行动，例如“此邮件可能更新 #329”。
2. **今日工作台/项目视图**：展示任务状态、项目风险、最近变化、建议下一步；不必每次聊天。
3. **全局任务型 AI**：用户可说“整理 CRM 所有未解决事项，并分别准备跟进草稿”；系统执行调查→方案→审阅→执行流程。

### 3.3 人和 AI 的自然分工

| 环节 | AI | 用户 |
|---|---|---|
| 信息收集 | 在授权范围内查找/分析邮件、附件、事项 | 可手动打开并核对证据 |
| 事项发现 | 提取候选工作信号及重复检测 | 确认、修正、忽略 |
| 项目归类 | 建议自动关联已有项目 | 纠错；维护项目边界 |
| 状态更新 | 依据新证据提出变化建议 | 对重要状态变更确认 |
| 写信 | 拟草稿、建议收件人、说明依据 | 核实收件人、加密方式、附件与正文 |
| 发送及外部操作 | 仅在授权后调用已校验工具 | 保留最终确认权 |

## 4. 事项识别：不要把邮件等同于任务

### 4.1 AI 先识别 Work Signals

从邮件中提取以下信号而非直接创建任务：

- **Action Request**：要求我或其他人完成某项工作。
- **Commitment**：承诺在某时间前处理，但是否由我负责需要确认。
- **Status Update**：已有事项的新进展。
- **Decision**：正式决策及其证据。
- **Blocker/Dependency**：阻塞、等待外部人员或前置条件。
- **Informational**：仅供知悉，不应创建待办。

### 4.2 候选→匹配→建议→正式状态

```text
邮件/会话更新
  → AI 抽取候选信号（需带原文引用）
  → 与已有任务、会话、项目匹配
      ├─ 新工作：进入 AI 发现队列（候选）
      ├─ 已有工作：提出增量更新建议
      └─ 信息不足：待确认/忽略，不硬归类
  → 用户确认或按事先批准的有限规则自动处理
  → 保存正式状态、变更日志及证据链接
```

**关键语义区别：**

- 回复了一封邮件 ≠ 完成了事项。
- 客户说“预计完成” ≠ 客户已经完成。
- 没找到客户回复 ≠ 证明客户没有回复或事项未完成。
- 用户建议“后续跟进” ≠ 已实际跟进。
- **AI 识别待审核状态**与**任务自身业务状态**是两个维度。

### 4.3 避免重复、误关联

- 一个事项可能关联多个邮件会话；一封邮件也可能产生多个事项。
- 结合会话 ID、主题、时间、项目上下文、参与人员、具体目标，而非仅靠标题关键词。
- 消息重新同步、重新导入、AI 重跑应具备幂等性，不能重复创建任务或历史事件。
- 用户拒绝/纠正后应记录反馈，不应在下次分析时重复犯同样的错误。

## 5. 项目识别：系统分类和项目实体分离

当前 Excel 的“系统”字段如 `CRM`、`BI`、`B/OSS`，它是业务分类，**不是自动等同于具体项目**。

建议 Project 具备：名称、别名、概述、成员、关联事项、邮件/附件、决策、风险、时间线和归档状态。

项目归类规则建议：

1. 有明确关键词、已知会话关联时可自动建议匹配。
2. 多项目共有人员或术语时，必须降低确定性，避免仅凭发件人归类。
3. 不确定时允许“不归类”；支持人工修改、项目别名、合并/拆分和归档。
4. 项目本身不等于邮件文件夹；项目和邮件的关联存储于本地工作数据库，不擅自移动服务器邮件。

项目页内容建议：**AI 概览（带出处）→ 正式任务 → 最新变化 → 阻塞/依赖 → 已确认决策 → 邮件和附件 → 成员**。

## 6. 工作记忆：长期可追溯而非聊天上下文

### 6.1 建议采用三层数据

1. **Evidence / 原始证据层**：邮件、会话、附件、来源账号、邮件服务端标识、Message-ID、时间、可定位片段。保持不可被 AI 擅自重写。
2. **Structured Work Memory / 结构化工作层**：Task、Project、Person、Decision、Dependency、TaskEvent、EvidenceLink；具有状态和版本历史。
3. **Personal Preferences / 个性化偏好层**：写信风格、常用联系人、用户明确认可的习惯；可查看、修改、删除。

不得把模型生成的一次摘要直接覆盖已确认的事实。重要对象至少记录：`来源/证据`、`确认状态`、`何时变化`、`由谁发起/审核`、`之前值`。

### 6.2 建议的数据对象（仅逻辑模型）

| 对象 | 关键属性/关系 |
|---|---|
| `Task` | 不变 ID、标题、系统分类、项目、状态、责任人、日期、优先级、阻塞、下一步、验收口径 |
| `TaskEvent` | 时间、动作、原始/新状态、变更理由、操作者、依据 |
| `Project` | 名称/别名、背景、成员、任务、决策、风险、归档 |
| `Decision` | 决策内容、适用范围、确认人、时间、证据、是否被后续取代 |
| `Evidence` | 邮件/附件来源定位、内容位置、时间、权限标签 |
| `TaskEvidenceLink` | Task↔Evidence 多对多关系、关联理由、是否人工确认 |
| `Person` | 通讯录身份、别名、组织关系、项目角色；不假设同名即同一人 |
| `AIProposal` | AI 对任务/项目/邮件的建议，待审/接受/拒绝/纠正 |
| `Preference` | 用户明确允许持久化的个人工作偏好 |

初期不需要为上述每一项都设计独立复杂服务；先评估基于 SQLite 的简单可迁移方案。

## 7. Excel + ChatGPT Work 任务体系迁移（应作为第一批工作）

### 7.1 当前任务管理的事实 [已确认：附件]

- 管理文件：`未完成任务.xlsx` + `已完成任务.xlsx`。完成任务归到“已完成”，取消任务归到“已取消”，当前清单不重复留存归档任务。
- 两份工作簿约定为 **15 列**；本次仅提供未完成工作簿，其表头在第 4 行。
- 本次上传的未完成表有 **5 条非终态任务**：`#302`、`#329`、`#330`、`#332`、`#333`。
- 当前五条的状态：`#302 受阻`、`#330 进行中`、其余三条 `未开始`；本次提供的表中五条“计划完成日期”均为空，**不能判逾期**。
- 完整归档历史、最终总量及跨文件编号唯一性：**因未提供 `已完成任务.xlsx`，此次不作完整验收声明**。

当前五条示例：

| ID | 分类 | 简要任务 | 状态 |
|---|---|---|---|
| 302 | CRM | DMZ 应用到 IT 数据库的网络连接排查 | 受阻 |
| 329 | CRM | OT CRM 对接 IT 用户 AD/LDAP 鉴权 | 未开始 |
| 330 | CRM | DMZ 服务器通过独立账号读取邮件 | 进行中 |
| 332 | B/OSS | 跟进 DWDM 与 MPLS-TP 三类网络运维报告 | 未开始 |
| 333 | CRM | 三名 CRM 用户账号与登录/请求流转验证 | 未开始 |

### 7.2 必须兼容的 15 个 Excel 字段

1. 编号
2. 系统
3. 任务内容
4. 优先级
5. 状态
6. 最新进展
7. 负责人／责任边界
8. 开始日期
9. 计划完成日期
10. 结束日期
11. 阻塞与依赖
12. 下一步
13. 最近更新日期
14. 进展与历史记录
15. 完成／验收标准

不得忽略长文本、换行、Excel 日期序列或空白值；导出应支持这 15 列可读的往返映射，新增内部字段可另设扩展导出。

### 7.3 必须保留的工作管理规则

- 任务编号唯一且稳定；迁移、归档、排序、更新不能改号；不能用行号公式做永久标识。
- **状态枚举**：未开始、待处理、进行中、受阻、待验收、已完成、已取消。非终态不可错误归档；历史阻塞不代表当前必须是“受阻”。
- 明确完成/取消才进行归档；“发邮件”“提交文档”等动作不等于整体项目/客户验收完成。
- 缺失的截止日期、优先级、责任人边界、验收事实**绝不推算或自动补造**。
- 用户明确说任务完成但没给日期，完成日期默认其**汇报当天的 Asia/Riyadh 日期**；若明确说日期，则以其指定日期为准。
- 负责人默认用户本人（除非任务明确另有责任人）；`BI` 指 `NG BI`，但 Excel 中系统字段继续保留 `BI`。
- “最新进展”保存最近确认的结果与问题；“进展与历史记录”不可丢失、不可被摘要替换。
- “下一步”是建议或计划，不能自动写成“已经执行”。
- 当前 ChatGPT Work 修改后须复读、核验，并列出全部未完成任务及总数；新工具应提供等价的**可核验任务清单与状态变更确认**。
- 已有 Git 历史和备份必须保留；切换后仍需可靠数据库备份及可导出的变更日志。

### 7.4 推荐迁移方式：四步，单一写入源

**阶段 A：无损读取与映射（只读）**

- 读取两本 Excel（包括已完成、已取消 Sheet）、任务规则、必要的历史说明。
- 建立字段映射和校验报告；检查编号、空值、状态、历史、日期、同任务多来源。
- 不修改原始 Excel，不合并/推断不明确的任务。

**阶段 B：并行校验（ChatGPT Work 仍为唯一写入方）**

- 鸿雁只读同步展示，并通过测试任务模拟更新/归档操作。
- 实际对比相同输入下鸿雁产生的状态与现有业务约定是否一致。
- 不允许 Work 和鸿雁同时修改正式任务源。

**阶段 C：切换正式数据源**

- 设定一次迁移窗口；停止 Excel 写入，做最终增量导入和校验。
- 鸿雁本地任务数据库成为唯一写入源；Excel 改为备份/导出/报告。
- 需具备回滚机制；确认正式切换前不能丢弃旧 Excel 或 Git 历史。

**阶段 D：开启 AI 邮件自动化**

- 邮件和任务关联 → 候选进展建议 → 项目记忆 → 受控 Agent 执行。

**原则：先迁移已存在的真实工作体系，再让 AI 学会从邮件理解新的事项。**

## 8. 邮件与任务如何关联

### 8.1 必须支持的交互

**读邮件时：**

> “这封邮件可能更新了任务 #329：客户提供了部分 LDAP 参数。建议记录客户反馈，但尚不能确认配置已经开始。”
>
> [查看来源] [关联到任务] [接受建议] [忽略/纠错]

**看任务时：**

> “#302 当前受阻：10 月 1 日请求开放网络、10 月 6 日已再次跟进；暂无可靠证据表明链路已经恢复。”
>
> [打开邮件] [完整时间线] [准备跟进草稿]

**从项目看全局时：**

> “CRM 部署项目目前受阻事项、等待外部反馈、最近决策、待核实风险有哪些？”

**用自然语言时：**

> “329 的 LDAP 信息客户发来了，但我们还没开始配置。”
>
> AI 找到 #329，提议追加进展和解除某个信息依赖，**不自行宣布鉴权已经成功**。

### 8.2 链接设计 [待技术验证]

- 保存**本地任务 ID** 与**原邮件稳定定位信息**（含账号/邮箱范围、Message-ID、服务端邮件 ID/文件夹、会话标识等可用信息）。
- 注意单独的 RFC Message-ID 在不同账号/共享邮箱、重复邮件、移动邮件时可能不足以稳定定位；需结合 Coremail 实际 ID 机制测试。
- 引用可以跳转邮件/附件具体位置；原邮件删除、移动、账号退出、缓存清理时应明确显示“证据暂不可用”，不能伪装可访问。
- **全文检索/语义索引**是新能力；已有密文 SQLite 缓存不可简单假定可运行普通明文 FTS。
- 附件内容的 AI 提取需要独立讨论解析能力、错误标记、加密与恶意文件风险。

## 9. AI / Agent 建议架构与工具边界

```text
UI 层
  今日工作台 / 邮件三栏 / Task Center / Project Center / AI Command
      ↓
应用服务层
  已有 Coremail 业务逻辑 + 新任务服务 + 项目服务 + 审计/通知
      ↓                    ↕
AI Orchestrator          Encrypted Local Work Store
  模型网关                 Task/Project/Events/Evidence/Preferences
  检索/RAG
  工具调用与状态持久化
  权限/策略/审批/审计
      ↕
DeepSeek API / 合规的企业模型或本地模型（可替换）
```

**模型只提出意图及工具调用；服务端应用代码验证参数/权限并执行。**

可参考的逻辑工具接口：

```python
search_mail(query, scope, limit)
get_mail(mail_ref)
get_conversation(thread_ref)
extract_attachment_text(attachment_ref)
find_contact(query)
list_tasks(filters)
get_task(task_id)
propose_task_update(task_id, changes, evidence_refs)
create_task_proposal(data, evidence_refs)
create_reply_draft(mail_ref, body, recipients)
link_task_to_mail(task_id, mail_ref)
confirm_proposal(proposal_id)    # 真实执行之前必须校验权限和状态
```

接口名仅为说明意图；实际签名、同步/异步机制、工具幂等和错误码应由 Claude 根据当前工程确定。

### 9.1 风险与自主权层级

| 操作级别 | 示例 | 建议策略 |
|---|---|---|
| 只读 | 搜索、读取已获授权邮件、总结、查看任务 | 可以自动执行，依权限隔离 |
| 建议类 | 抽取任务、预测归属、拟定邮件草稿 | AI 可自动生成，结果标记“待审核” |
| 内部写操作 | 修改正式任务、归档、创建项目、重新归类 | 先以审核式写入为主，记录前后差异并支持撤销 |
| 外部/高风险 | 发送邮件、改变主送/抄送、外发附件、删除、权限修改 | 明确展示详情并要求用户确认，绝不静默执行 |

邮箱正文、附件、外部邮件中的“指令”只是**不可信内容**，不能被当成开发者/系统指令执行；防范 Prompt Injection。

### 9.2 DeepSeek 与安全部署 [待验证]

- 首要问题不是选哪个模型，而是**公司是否允许真实邮件、附件、解密后的 S/MIME 内容进入公共云 AI API**。
- 若无法获得授权，必须支持“AI 功能关闭 / 仅本地处理 / 企业授权范围调用”等策略；不得通过 HTTPS 就宣称合规。
- 单独确认日志和遥测是否可能泄露标题、正文、密钥、附件内容或人员信息；密钥不可硬编码和写入 Git。
- 模型 API 的具体名称、上下文窗口、工具调用兼容性、价格、隐私政策、接口限流等可能变化，Claude 应核对官方文档，不要照搬讨论时的模型名称。
- 将模型驱动与 Coremail 业务逻辑解耦，日后便于替换模型、增加本地模型或企业私有服务。

### M1：任务中心与 Excel 无损迁移（第一交付闭环）

## 12. 最小可行产品（MVP）与验收

### MVP 最小场景

> 用户把现有两份 Excel 导入鸿雁 → 首页可看到全部真实未完成任务 → 打开 #302 查看历史 → 在鸿雁直接新增进展 → 检查变更差异 → 保存并生成时间线 → 导出 Excel 后仍能找回全部历史。

随后叠加第一条安全 AI 场景：

> 用户手动打开一封邮件 → 选择“分析与关联任务” → AI 建议关联 #329 或创建新候选事项 → 显示邮件原文证据与判定理由 → 用户纠正或接受 → 更新工作记忆。

### 关键验收案例（Claude 可扩充为自动化测试）

1. **Excel 字段无损**：15 列往返，长文本不截断，日期值一致，空值保留。
2. **编号稳定**：归档、排序、多次导入不改号、不重复，已完成/已取消分别正确归档。
3. **保留历史**：新进展追加事件，而不是覆盖“进展与历史记录”。
4. **谨慎状态转换**：邮件说“预计周五解决”，不得判已完成；没有日期不得判逾期。
5. **迁移准确**：未完成数、完成数、取消数、重复数和异常单元格可核验；样本与原文件逐项对照。
6. **消息关联稳定**：移动邮件、同主题不同会话、共享邮箱等情形均不会错误指向另一封邮件。
7. **权限与数据安全**：真实公司邮件未经授权不发送至公共 API；敏感日志不落盘。
8. **安全执行**：高风险操作需要确认，工具拒绝越权/危险参数，邮件内容不能触发越权指令。
9. **恢复和回滚**：断电/异常后任务事务一致，备份可恢复，AI 长任务可安全重试。
10. **不用 AI 也好用**：核心 Task Center 和传统邮件视图在离线/模型不可用时仍可操作。

## 15. 本轮讨论已达成的共识与尚未决定的关键事项

### 已达成共识

- 定位为 **AI 原生工作助手**，而不是“集成 DeepSeek 聊天框的邮箱”。
- 产品信息架构采用 **任务 + 项目融合**，邮件保留为原始沟通与证据来源。
- **先迁移既有 Excel 管理体系**，避免丢失历史；再逐步做邮件智能、项目记忆与 Agent。
- 保留现有邮件操作效率，不强制所有操作通过 AI 聊天。
- 信息整理尽可能自动化、工作判断适度自动化、对外操作严格受控。
- AI 不能静默篡改正式任务、无证据地生成完成结论，也不能擅自发送邮件。
- 任何长期工作知识必须持久化本地，并能够追溯、纠错、导出和恢复。

### 需要 Claude Code 结合源码回答后再决定

- 当前代码实际能复用到什么程度，AI 目录是否存在部分可靠实现。
- Task Center 最小数据模型、界面载体、持久化/加密、数据库迁移方式。
- 是否引入 Agent 框架、向量索引/向量数据库，以及引入时机。
- 适合当前 Windows + 公司网络环境的模型部署与安全边界。
- Excel 双工作簿全部历史记录的正式迁移核验结果。
- 人工审阅比例、候选任务自动入队条件、提醒机制与默认主页。

---

**最终目标不是让用户向 AI 发出更多指令，而是让用户在正常收发邮件、处理项目与汇报进展时，鸿雁能可靠地理解工作、维护历史、发现关联，并协助推进下一步。**
