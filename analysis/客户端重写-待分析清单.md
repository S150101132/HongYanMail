# 自研邮箱客户端：还需要分析什么

日期：2026-10-16。基线：`analysis/客户端-服务器接口清单.md`（138 个接口名 / 客户端可用 130 个）+ 现有 `coremail_desktop` 预览版实现。
本文只讲"要重做一个可用客户端，还缺哪些逆向与契约证据"，不重复已完成部分。

| 服务端搜索 | `XT/jsp/mail.jsp?func=searchMessages`，仅契约验证，UI 未接 |

**接口覆盖率：130 个客户端可用接口中，已接入约 10 个，未接入约 120 个。**

### 本轮已推进（2026-10-16）

| 项 | 结果 |
| --- | --- |
| P0 错误码表 | 从二进制枚举出 **54 个 `FA_*` 服务端错误码**（会话/二次认证/密码策略/登录限制/业务），见 `P0-认证与会话-证据.md`。日志中 `FA_*` 出现 0 次 → 处理动作只能靠契约验证 |
| P0 认证字段 | 登录/设备/令牌相关字面量逐项定位（`accessToken`/`accessSecret`/`accessNonce`/`signature`/`user:setDeviceSecret`/`user:getTempSession` 等） |
| P1 字段契约 | 建了日志契约抽取器 `tools/extract_contracts.py` → `analysis/runtime-interface-contracts.json` |
| **重要负面结论** | **运行日志不足以恢复接口契约**：只对少数接口记录请求体（如 `user:getAttrs{attrIds,optionalAttrIds}`、`user:listDelmsgHistory{limit,loginType,start}`、`mbox:getComposeInfo{id}`），响应通常只记录 `{code}`，完整响应只有 `mbox:getAllFolders` 一类；失败分支不记录。→ P1 的字段/返回 schema **必须**走服务端契约验证或原生反编译，不要指望日志 |
| 数据安全 | 日志请求行含同域其他同事邮箱与会话痕迹，已约束抽取产物只保留字段名与类型 |

## 1. 差距总览

| 优先级 | 主题 | 关键缺口 | 影响 |
| --- | --- | --- | --- |
| **P0** | 认证与会话生命周期 | 设备绑定/密钥登录、二次认证、会话续期、错误码全集 | 换部署或换账号即登录失败，其它全废 |
| **P1** | 邮件核心闭环 | 服务端附件下载、删除/恢复/废纸篓、线程、标签、收件人校验、共享邮箱 | 只能"看和回"，不能当日常客户端 |
| **P2** | 组织数据 | 企业通讯录（oab）、个人通讯录（pab）、头像、**组织架构增量同步** | 无自动补全、无头像、无组织树 |
| **P3** | 安全与合规 | S/MIME 与国密提交、加密邮件解密、本地库加密格式 | 客户要求的加密收发无法交付 |
| **P4** | 实时性与离线 | 新邮件推送（SSE/Socket.IO）、增量同步、离线库 | 只能手动刷新，无离线能力 |
| **P5** | 扩展功能 | 日历会议、网盘、规则/自动回复、签名、应用专用密码 | 与原客户端功能差距明显 |
| **P6** | 工程与协议版本 | XT3/XT5/XT6 差异、路由稳定性、代理/证书、遥测合规 | 只能在单一部署上工作 |

## 3. 每类结论该用什么证据

| 证据类型 | 适用问题 | 本机现状 |
| --- | --- | --- |
| 契约验证脚本（`analysis/*-contract-*.json` 模式） | 单接口的参数/返回/错误语义 | 已有成熟先例，成本最低，优先 |
| 抓包（HAR / SAZ） | HTTP method、完整字段、错误码、推送帧 | 未安装 mitmproxy/tshark；REA 可离线解析 HAR/SAZ |
| 运行期只读观察 | CEF 网页层与原生桥的实际调用序列 | REA 提供 `list_javascript_runtime_targets`、`list_browser_targets` 等工具，未启用 |
| 原生反编译 | 调度表、参数拼装、加密实现 | Ghidra 12.1.4 已装；40 MB 目标超出 330 s 分析截止，需拆目标或放宽时限，并给 MCP 注册补 `GHIDRA_INSTALL_DIR` |
| 原客户端日志对比 | 判断哪些接口被真实高频使用 | 已有 73 个日志、57,498 次调用命中，可继续作为"重要性排序"依据 |

## 4. 建议顺序

1. **P0 认证**：先用契约验证覆盖二次认证与设备绑定分支，再决定是否支持"密钥登录"。
2. **P1 读→写闭环**：服务端附件下载、删除/恢复、移动 UI、线程、`validateRcpts`、共享邮箱切换。
3. **P2 通讯录 + 组织架构增量同步**：直接决定日常可用性（自动补全、头像、组织树）。
4. **P4 推送**：拿到 SSE/Socket.IO 契约，替换手动刷新。
5. **P3 加密**：在明确客户合规要求（S/MIME vs 国密）后再投入；未验证前保持"明确拒绝"。
6. **P5/P6 扩展与适配**：按目标部署版本（XT?）逐项验证，不假设跨版本一致。

## 5. 红线（沿用现有约定）

- 不复制、不伪造原客户端的设备身份与密钥；设备绑定走正常协商。
- 加密提交接口未完成真实双向验证前，不静默降级为明文发送。
- 遥测类接口（`clickLog`、`log/report`、跟踪数据）默认关闭并显式说明。
- 本地邮件库加密格式未确认前，不尝试解密或迁移既有 `mail.edbx2`。
- 只在本人账号与明确授权的测试邮件上做验证，测试邮件保留不删除。
