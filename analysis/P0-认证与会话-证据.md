## 4. 仍然未知（必须靠新证据）

| 未知 | 影响 | 需要的证据 |
| --- | --- | --- |
| 每个 `FA_*` 的后续动作 | 无法正确引导用户完成验证/绑定 | 受控失败重放（错误密码、错验证码）记录响应码 + 后续字段 |
| `getPasswordKey` 公钥的算法/填充/编码/时间戳拼接 | 无法实现"加密密码登录"分支 | 反编译 `checkPasswordEncryptType` 邻近实现，或抓包对比 |
| `accessToken + nonce + signature` 的原文拼接与摘要算法 | 无法实现设备密钥登录 | 二进制邻近字符串 + 反编译；不得复制原客户端密钥 |
| 设备注册协商（`user:setDeviceSecret`）的合法流程 | 首次登录被要求"绑定可信设备"时无法自助完成 | 契约验证 + 服务器返回 |
| `user:getTempSession` / `triggerSecondAuth` 的状态机 | 二次认证无法闭环 | 契约验证 |
| `user:authenticate2` 的真实用途 | 目前邻近证据指向"安全文件夹解锁"，非登录第二因素 | 反编译控制流 |
| sid 有效期与续期触发点 | 长会话会突然失效 | 观察日志中的 sid 变化与 `FA_UNAUTHORIZED` 出现 |
| 并发登录/多端策略 | 无法正确提示 | 契约验证 |

## 5. 给自研客户端的结论

1. **可以继续用普通表单登录**：它已被真实验证，且与设备密钥分支解耦。
2. **设备绑定与二次认证只能"明确阻断 + 引导用户到官方渠道"**，除非补齐上表证据；不允许静默伪造设备身份。
3. **错误码表可以直接落地**：54 个码可作为枚举，但每个码的处理动作需要逐个验证，不能凭名字猜测。
4. **日志不能替代契约测试**：本轮已确认日志只记录部分请求体、几乎不记录完整响应（见 `analysis/runtime-interface-contracts.json`），失败分支的错误码在日志中完全不出现。

## 6. 数据安全提示（本轮发现）

客户端运行日志的请求行里包含**同域其他同事的邮箱地址**（`uid=<name>%40inspur.com`）以及会话与签名痕迹。因此：

- 不要把原始日志复制进仓库、工单或报告；
- 任何衍生产物只保留字段名与类型（本轮的抽取脚本即按此约束，只写 key 名与类型）；
- 需要分享样本时先做邮箱/令牌脱敏。
